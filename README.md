# KRM РФ — инструкция по работе с проектом

## Что это за проект

KRM РФ — статический сайт-архив о Кременной, ЛНР, восточном фронте, гражданских последствиях и практических справках.

В проекте нет CMS, базы данных и панели администратора. Публикации хранятся как обычные `index.html`, а `data/pages.json` содержит каталог публикаций и их SEO-метаданные. Node.js-скрипты собирают и проверяют главную страницу, разделы, архив, поиск, sitemap, карту и публичный каталог `dist/`.

Публичный сайт разворачивается на GitHub Pages только из `dist/` после попадания проверенных изменений в `main`.

## Ветки и безопасный workflow

- `noviy-sait` — рабочая/тестовая ветка;
- `main` — production-ветка, из которой выполняется GitHub Pages deploy.

Обычная последовательность:

**изменение → локальная проверка → просмотр `dist/` → просмотр diff → commit → push в `noviy-sait` → зелёный Quality → проверка → merge `noviy-sait` → `main` → production deploy**.

Не отправляйте изменение карты или другой технической части сразу в `main` и не делайте push до прохождения проверок.

## Структура проекта

- `index.html` — главная;
- `news/` — материалы и справочные публикации;
- `assessment/` — датированные оценки фронта;
- `war-crimes/` — досье;
- `map/index.html` — HTML страницы карты;
- `assets/js/map.js` — логика карты;
- `assets/css/page-map.css` — стили карты;
- `data/zones.geojson` — текущая геометрия карты;
- `data/map-changes.json` — описание последнего изменения карты;
- `data/map-places.json` — локальный справочник населённых пунктов;
- `data/map-history/` — производный кэш последних срезов для селектора карты;
- `data/map-archive/` — постоянный журнал и исходные геометрии всех доступных срезов; сохраняются в Git и release;
- `data/map-statistics.json` и `.csv` — воспроизводимая статистика, создаётся сборкой;
- `MAP_STATISTICS.md` — методика статистики, обновление истории и получение текста для канала;
- `data/rf_regions.json` — административные границы;
- `data/pages.json` — каталог публикаций и SEO-метаданные;
- `data/content-integrity.json` — контроль видимого содержимого публикаций;
- `tools/` — сборка, валидация, экспорт, release и проверки;
- `tests/e2e/` — Playwright E2E;
- `.github/workflows/quality.yml` — один QA на актуальный push рабочей ветки (PR не запускает второй QA);
- `.github/workflows/pages.yml` — QA и production deploy после push/merge в `main`;
- `.github/workflows/release.yml` — только ручной одноразовый снимок текущей версии, без запуска по тегам;
- `_redirects` — внутренний реестр старых URL; GitHub Pages его напрямую не исполняет;
- `dist/` — готовый публичный сайт; в Git не сохраняется.

## Основные проверки

Полная обязательная проверка:

```bash
npm run qa
```

`npm run qa` выполняет обработку изображений, сборку, HTML/SEO/link validation, smoke-тесты, performance budgets, контроль содержимого, idempotence, чистоту export, создание `dist/`, проверку публичной сборки и карты, runtime smoke и Playwright E2E. Проверка карты запускается после экспорта, чтобы читать свежий `dist/`.

`map:verify` проверяет исходники и существующий `dist/`. Для отдельной проверки после изменений сначала обновите публичную сборку:

```bash
npm run build &&
npm run export:public &&
npm run map:verify
```

Но перед commit/push технического изменения карты всё равно выполняйте полный:

```bash
npm run qa
```

После успешного QA готовая публичная версия находится в `dist/`.

## Аналитика ключевых действий

`assets/js/metrika.js` использует один существующий счётчик Яндекс.Метрики и отправляет технические JavaScript-события без текста поисковых запросов:

- `home_route` — переход с главной на другой внутренний URL;
- `search_submit` — отправка локального поиска (только длина и число слов);
- `search_result_click` — открытие результата поиска;
- `map_action` — выбор среза, сравнение, поиск населённого пункта, fullscreen и копирование ссылки;
- `channel_click` — переход в Telegram или MAX;
- `source_click` — переход по внешнему источнику, без передачи полного URL;
- `read_depth` + `read_50`/`read_90` — достижение 50% и 90% публикации;
- `content_continue` — переход из публикации на другой внутренний URL; якоря той же страницы не считаются.

UTM для Telegram/MAX описаны в `ANALYTICS_UTM.md`; готовые ссылки создаёт `npm run utm`. UTM не размножаются по внутренним ссылкам: стандартная атрибуция Метрики сохраняет источник визита. Код сайта не зависит от наличия целей и при блокировке Метрики продолжает работать.

## Единообразие публикаций

Существующие правила каркаса, оглавлений, метаданных и соседних переходов описаны в `PUBLICATION_LAYOUT.md`. Служебные блоки нормализуются командой `npm run build`; `npm run validate` проверяет их согласованность. Содержание статей сборка не переписывает.

## Актуальность практических памяток

Исторические статьи сохраняют дату публикации и не получают вводящую в заблуждение пометку «актуально сегодня». Для действующих памяток используются отдельные поля `reviewedAt`, `reviewAfter`, `reviewCadenceDays` и `reviewStatus` в `data/pages.json`.

После фактической проверки ссылок, опубликованных контактов, сумм, сроков и нормативных оснований зафиксируйте её для конкретной памятки:

```bash
npm run guides:review -- --id=chto-delat-pri-atake-bpla-lnr --date=YYYY-MM-DD
npm run build
npm run test:freshness
```

`--id=ID` можно повторять. Без `--id` команда обновляет все действующие памятки — используйте этот режим только после проверки всех. Неизвестный или пустой ID и неизвестная опция останавливают команду без записи. `npm run test:freshness -- --id=ID` проверяет выбранную памятку, а штатный QA по-прежнему проверяет весь справочник. Редакционную проверку отличайте от фактического ответа телефонной линии или успешной подачи заявления; незавершённую сверку фиксируйте отдельно и не переносите срок ради успешного CI.

Команда назначает следующую проверку через 30 дней. Обычный QA предупреждает за 7 дней до срока и блокирует просрочку. Ежедневный GitHub Actions-контроль использует --strict-warning и сигнализирует уже за 7 дней. `reviewedAt` не заменяет `dateModified`: дату изменения материала повышайте только при реальной редакционной правке.

## Как добавить публикацию

1. Создайте новую папку и `index.html` в подходящем разделе.
2. Добавьте запись в `data/pages.json`.
3. Проверьте `id`, `url`, `type`, `section`, `datePublished`, `dateModified`, SEO-поля, изображение и `alt`.
4. Если добавлен/изменён видимый текст, ссылки или смысловой `alt`, обновите контроль содержимого:

```bash
npm run images
npm run build
npm run content:lock
```

5. Выполните:

```bash
npm run qa
PORT=8080 npm run serve:dist
```

6. Проверьте публикацию, главную, нужный раздел, архив, поиск и мобильный вид.

При изменении только CSS/JS `npm run content:lock` не нужен. Текст оглавлений и ссылки нижней навигации входят в существующий контроль содержимого: после их осознанного изменения сначала выполните сборку и просмотрите diff, затем обновите контроль. Не используйте `content:lock` для подавления неожиданного изменения текста.

## Как обновить старую публикацию

После осознанного содержательного изменения:

1. измените её `index.html`;
2. обновите `dateModified` в `data/pages.json`;
3. при необходимости обновите `revisionHistory`;
4. выполните:

```bash
npm run images
npm run build
npm run content:lock
npm run qa
PORT=8080 npm run serve:dist
```

Не повышайте `dateModified` из-за чистого CSS/JS/build-изменения.

## Изменение карты

### Если меняется геометрия/редакционный срез

Обычно изменяются:

1. `data/zones.geojson`;
2. первая актуальная запись `data/map-changes.json`.

`zones.updated` и `changes[0].zonesUpdated` должны совпадать. История редакционных срезов создаётся `tools/map-history.mjs` из текущего файла, постоянного архива, старого кэша и доступной полной Git-истории. `npm run build` одновременно пересчитывает статистику. Новые файлы `data/map-archive/` нужно включать в commit вместе с изменением карты, чтобы промежуточные срезы переживали squash/rebase. Подробности и генератор постов: [MAP_STATISTICS.md](MAP_STATISTICS.md).

Все GitHub workflow, которые строят или проверяют карту, должны использовать `actions/checkout` с `fetch-depth: 0`. Не убирайте это: shallow checkout меняет полноту истории карты.

### Если исправляется поведение карты

Изменяйте только реально нужные файлы, например:

- `assets/js/map.js` — камера, поиск, permalink, история, compare/fullscreen;
- `assets/css/page-map.css` — размеры и адаптивность;
- `map/index.html` — разметка и подключения.

### Обязательная последовательность после любого изменения карты

Сначала:

```bash
npm run build
npm run export:public
npm run map:verify
npm run qa
PORT=8080 npm run serve:dist
```

Затем вручную проверьте:

1. чистый вход на `/map/` без `lat`, `lng`, `z` — карта должна открываться в редакционном стартовом положении;
2. hard reload;
3. desktop;
4. mobile portrait;
5. mobile landscape;
6. загрузку зон, административных границ и ориентиров;
7. поиск населённого пункта;
8. кнопку «Вся карта»;
9. fullscreen и возврат;
10. прямую ссылку `/map/?lat=...&lng=...&z=...` — заданная камера должна сохраняться;
11. UTM/другие посторонние query-параметры не должны исчезать при движении карты;
12. после полной загрузки не должно быть второго неожиданного перемещения;
13. если доступна история — выбор редакционного среза и сравнение;
14. статистику последнего обновления, дня, месяца и копирование текста поста.

Только после этого переходите к commit/push.

## Проверка diff и commit

Перед staging:

```bash
git diff --check
git status
git diff
```

Добавляйте только ожидаемые файлы, а не весь рабочий каталог вслепую:

```bash
git add <нужные-файлы>
git diff --cached
git status
```

Если staged diff соответствует задаче:

```bash
git commit -m "Краткое описание изменения"
git push origin noviy-sait
```

После push дождитесь зелёного workflow **Quality**.

## Merge `noviy-sait` → `main`

После зелёного **Quality** и ручной проверки создайте pull request из `noviy-sait` в `main` и ещё раз просмотрите итоговый diff.

Merge выполняйте только если:

- QA прошёл;
- diff просмотрен;
- тестовая версия работает;
- для карты отдельно проверены стартовая камера, mobile и permalink;
- нет случайных файлов.

После merge/push в `main` `.github/workflows/pages.yml` снова выполняет `npm run qa`, создаёт `dist/`, загружает только `dist` как Pages artifact и выполняет официальный GitHub Pages deploy.

Настройки branch protection и правила merge находятся в GitHub, а не в архиве проекта; при их изменении ориентируйтесь на фактические настройки репозитория.

## Sitemap и `lastmod`

Не меняйте `lastmod` только потому, что файл технически пересобран.

Текущие правила:

- публикации получают `lastmod` из `dateModified` в `data/pages.json`;
- `/map/` получает `lastmod` из `data/zones.geojson.updated`;
- главная и разделы получают даты из актуальных публикаций;
- `/about/`, `/methodology/`, `/privacy/` получают `lastmod` из `<meta name="date-modified" content="YYYY-MM-DD">` внутри соответствующей страницы.

Если содержательно меняются `/about/`, `/methodology/` или `/privacy/`, обновите их `date-modified`. Для чистой технической правки дату не повышайте. `npm run build`/`npm run qa` синхронизирует sitemap автоматически.

## Версия и cache busting

Локальные CSS/JS подключаются с `?v=<package version>`. Если технический release изменяет клиентский CSS/JS, версия в `package.json` и `package-lock.json` должна быть повышена, после чего `npm run build` автоматически синхронизирует query-версию во всех HTML. Это нужно, чтобы production-браузеры не продолжали использовать старый закэшированный файл.

Не меняйте номера `?v=` вручную по отдельным страницам.

## Что не редактировать вручную без причины

Обычно не редактируйте:

- `dist/`;
- `data/search-index.json`;
- `data/site.json`;
- `data/map-history/`;
- `data/map-statistics.json` и `data/map-statistics.csv`;
- сгенерированные карточки главной и разделов;
- `sitemap.xml`, если дата может быть получена из описанных выше источников.

Они создаются или синхронизируются сборкой.

## Старые URL

Старые адреса перечислены в `_redirects`, но GitHub Pages не исполняет этот файл как серверную конфигурацию. `npm run export:public` создаёт в `dist/` статические страницы переноса с `noindex`, canonical, `meta refresh` и JavaScript-сохранением query/hash.

Это известное ограничение текущего хостинга, а не настоящий серверный `301` прямо на новый материал.

## Релизные снимки (только если действительно потребуются)

Обычная публикация не создаёт архивов и не требует ручных ZIP. Единственный экземпляр сайта и его история изменений хранятся в Git / GitHub Pages. По желанию можно создать **один актуальный** проверенный снимок:

```bash
npm run release
```

Он перезаписывает `krmrf-source.zip`, `krmrf-public.zip` и `krmrf-release.json` в `../krmrf-releases/`. Старые версионные комплекты удаляются только после успешной QA, контрольных сумм и проверки нового снимка; неизвестные файлы не затрагиваются. Ручной вызов GitHub Actions `Release archives` хранит артефакт только один день. Перед удалением накопленных старых ZIP можно посмотреть `npm run release:cleanup:dry-run`. Ни push, ни merge, ни tag не создают релизных ZIP.

`npm run images` проверяет SHA-256 исходных и адаптивных картинок по `data/image-derivatives.json`. Если оригинал заменён, две WebP-копии создаются заново, даже если ширина старой копии осталась правильной.

Штатный production deploy всё равно выполняется GitHub Pages workflow из `dist/`; release ZIP не заменяет обычный deploy.

## Откат

Если изменение сломало тестовую ветку:

1. не merge в `main`;
2. отмените или исправьте проблемный commit в `noviy-sait`;
3. снова выполните `npm run qa`;
4. повторно проверьте `dist/`;
5. push исправления в `noviy-sait`.

Если поломка уже попала в production:

1. создайте revert/исправляющий commit;
2. прогоните `npm run qa`;
3. проведите исправление через `noviy-sait` и обычный merge в `main`;
4. дождитесь зелёного Pages workflow;
5. перепроверьте живой сайт.

Не смешивайте отдельные файлы из разных `dist`/ZIP-выпусков и не используйте force-push в `main` как обычный способ отката.

## Типичные ошибки проекта

- изменение карты и push до `npm run qa`;
- проверка только кнопок карты без проверки стартовой камеры;
- преобразование отсутствующих `lat/lng/z` в числа до проверки наличия параметров;
- удаление UTM при обновлении permalink карты;
- изменение `data/zones.geojson` без синхронной записи `data/map-changes.json`;
- shallow checkout в workflow, который строит историю карты;
- ручная правка `dist/` или других производных файлов;
- содержательная правка публикации без `npm run content:lock`;
- автоматическое повышение `lastmod` после чисто технической правки;
- изменение клиентского JS/CSS без повышения версии для cache busting;
- `git add -A` без просмотра того, что реально попадёт в commit;
- merge при красном **Quality**;
- проверка карты только на desktop.

## Техническая заморозка

До 29 июля 2027 года действует `TECHNICAL_FREEZE.md`: разрешены публикации, редактура, обновление карты и минимальные исправления подтверждённых поломок/уязвимостей. Не используйте реальный баг как повод для большого архитектурного рефакторинга, если он устраняется небольшим проверяемым патчем.

## Автоматическая подготовка и история статистики

Build создаёт ops/publish-links.json, ops/publish-links.tsv и ops/posts/<канал>/<id>.md. Новые статьи размечаются автоматически, для дополнительного канала достаточно записи data/utm-campaigns.json. В сводке карты выбирается Telegram/MAX. Отправку поста выполняет редактор. Однократные настройки счётчика и приватного API-сбора: [METRIKA_SETUP.md](METRIKA_SETUP.md). reviewedAt меняется только после настоящей проверки всех отмечаемых памяток.

При изменении подзаголовков сначала выполните `npm run build`, чтобы синхронизировать оглавление, затем просмотрите diff и выполните `npm run content:lock`. После фиксации ожидаемого содержания запустите полный QA.
