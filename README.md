# KRM РФ — работа с сайтом

**Сайт:** https://krmrf.ru · **платформа:** статический HTML + Node.js 24 · **публикация:** GitHub Pages из `dist/`.

Это рабочая инструкция владельца сайта. Основной принцип: **редактировать исходный материал и данные, дать скриптам собрать производные файлы, проверить и только затем публиковать**. Здесь нет CMS, личного кабинета или сервера для динамического сохранения статей. `dist/` не коммитится.

> **Быстрый маршрут:** новый материал → `npm run articles:prepare` → проверить изменения → `npm run content:lock` (только для сознательно изменённого текста) → `npm run qa:visible` → посмотреть `dist/` → commit/push в `noviy-sait` → зелёный Quality → merge в `main` → зелёный Deploy GitHub Pages.

## 1. Как устроен проект

| Где искать | Что это | Редактировать вручную? |
|---|---|---|
| `news/**/index.html`, `assessment/**/index.html`, `war-crimes/**/index.html` | Содержание каждой опубликованной страницы | Да, при редактировании материала |
| `data/pages.json` | Каталог материалов: ID, URL, H1, SEO, даты, раздел, обложка, таксономия | Да, для новой статьи и значимых правок |
| `data/taxonomy.json` | Разрешённые разделы, темы и географические метки | Только при осознанном расширении словаря |
| `assets/img/` | Оригиналы иллюстраций | Да, класть новые изображения |
| `assets/img/derived/`, `data/image-derivatives.json` | Адаптивные версии картинок и их SHA-256 | Нет: `npm run images` |
| `data/utm-campaigns.json` | Стабильные кампании, каналы Telegram/MAX | Обычно нет: `articles:prepare` добавит отсутствующие ID |
| `ops/publish-links.tsv`, `ops/posts/telegram/`, `ops/posts/max/` | Готовые UTM-ссылки и текстовые заготовки | Нет: `npm run build`; не коммитятся |
| `data/content-integrity.json` | Контроль текста и смысловых подписей публикаций | Нет: `content:lock` после редакционного просмотра |
| `data/zones.geojson`, `data/map-changes.json` | Текущая геометрия карты и описание правки | Да, только совместно |
| `data/map-archive/` | Постоянные исторические срезы и контрольные суммы | Нет вручную; **добавлять новые файлы в Git** |
| `data/map-statistics.json/.csv`, `data/map-history/` | Вычисляемая статистика и кэш выбора срезов | Нет: `npm run build` |
| `data/search-index.json`, `data/site.json`, `sitemap.xml`, карточки разделов | Производные материалы | Нет: `npm run build` |
| `tools/`, `tests/`, `.github/workflows/` | Автоматизация, проверки, развёртывание | Только при доказанной технической необходимости |
| `dist/` | Именно то, что будет опубликовано на GitHub Pages | Нет: создаётся автоматически |

Разделы: СВО (`news/svo/`), Кременная (`news/kremennaya/`), ЛНР (`news/lnr/`), гражданские последствия, политика, памятки, оценки фронта и досье. Поиск, главная, архив, sitemap и переходы между статьями строятся из реестра и текущих HTML. **Текст статей сборка не сочиняет и не сокращает**.

## 2. Подготовка Codespaces (один раз)

```bash
git switch noviy-sait
git pull --ff-only origin noviy-sait
nvm install 24
nvm use 24
npm ci
sudo apt-get update && sudo apt-get install -y imagemagick librsvg2-bin
npx playwright install --with-deps chromium
```

Рабочая ветка — `noviy-sait`. Публичная ветка — `main`. Если появился новый ZIP сайта, в нём **нет** `.git`, установленных npm-зависимостей и настроек GitHub: сначала восстановите репозиторий и среду. Подробнее: [RECOVERY.md](RECOVERY.md). Перед командами проверьте `node -v`, `git branch --show-current`, `git status --short`.

## 3. Новая статья: минимальное число действий

1. Создайте каталог, например `news/svo/svo-YYYY-MM-DD/index.html`, на основе **действующего** материала того же типа и его структуры. Не копируйте старые даты, canonical, JSON-LD, OG-теги и чужую обложку без проверки.
2. Добавьте статью в `data/pages.json`: уникальный `id`, путь `url` со слешами, `type`, `section`, `title` (H1), `seoTitle`, `seoDescription`, `excerpt`, `datePublished`, `dateModified`, `image`, `imageAlt`, подходящие `locations`/`topics`. Метки должны уже существовать в `data/taxonomy.json`.
3. Положите готовые изображения в `assets/img/<раздел>/<статья>/`. Не оставляйте `.gitkeep` в папке картинок. В HTML нужны реальные `src`, `alt`, `width` и `height`. В таблицах обязателен `<caption>`; `style="..."` запрещён строгой CSP. Для промежуточного HTML-фрагмента используйте `.fragment`, **не** `.html`.
4. Запустите единую подготовку:

```bash
npm run articles:prepare
```

Команда добавит **только отсутствующие UTM-кампании** с именем ID статьи (не изменяя старые), подготовит размеры изображений, синхронизирует разделы, поиск, sitemap, карту и ссылки, проверит стабильность UTM-тестами, затем каталог и HTML. Если неизвестна территория, нет картинки или обнаружена запрещённая разметка, команда **остановится с понятной ошибкой**, не подменяя ваши редакционные решения.

5. Просмотрите текст, даты, картинки и diff. Только после проверки осознанного изменения контента обновите контрольную сумму:

```bash
npm run content:lock
npm run qa:visible
```

`content:lock` **не** является способом скрыть неожиданное изменение текста. После успешной полной проверки откройте публичную сборку:

```bash
PORT=8080 npm run serve:dist
```

В Codespaces откройте порт `8080` и проверьте статью, главную, соответствующий раздел, поиск, архив и мобильную ширину. Остановить сервер: `Ctrl+C`.

**Обновление старой статьи:** редактируйте существующий HTML, измените `dateModified` только при реальном изменении содержания, повторите подготовку/просмотр/`content:lock`/QA. Для одной только CSS/JS-правки `content:lock` обычно не нужен.

## 4. Проверки: что запускать и как видеть прогресс

| Команда | Назначение |
|---|---|
| `npm run articles:check` | Быстрая **читающая** проверка всех зарегистрированных статей без зависимости от `.git` |
| `npm run articles:prepare` | Автоматически восполнить недостающие UTM, обработать изображения, собрать и валидировать |
| `npm run images` | Проверить исходные и производные картинки, SHA-256 и responsive-варианты |
| `npm run build` | Собрать статические разделы, sitemap, поиск, историю и статистику карты, ссылки для публикации |
| `npm run validate` | Проверить HTML, SEO, структуру каталога, таксономию, картинки и ссылки |
| `npm run content:check` | **Только проверить** защиту содержимого, без записи |
| `npm run content:lock` | Зафиксировать сознательно отредактированное содержимое |
| `npm run qa:visible` | Полная `qa`, но с этапами и регулярным индикатором работы; полный журнал `.cache/qa-last.log` |
| `npm run qa` | Та же полная проверка с подробным обычным выводом |
| `npm run test:negative` | Отдельные негативные сценарии валидатора; входит в `release`, не в стандартную `qa` |
| `npm run test:search-e2e` | Проверить поиск в Chromium через Playwright |
| `npm run export:public` | Пересобрать `dist/` из проверенных источников |
| `npm run validate:public` | Проверить публичную сборку `dist/` |

В `qa:visible` нельзя «зависнуть молча»: этап и время выводятся примерно раз в 20 секунд, а весь подробный лог остаётся в `.cache/qa-last.log`. Проверка может быть долгой из-за импорта истории карты и браузерных тестов. **Нельзя запускать две QA одновременно**. Код завершения `0` — успех; любое другое значение — разбирать журнал и не публиковать.

## 5. UTM-ссылки для Telegram и MAX

**Получить обе ссылки на конкретную статью:**

```bash
npm run utm -- --url /news/svo/svo-2026-10-21/ --both
```

**Одну ссылку для повторного поста:**

```bash
npm run utm -- --url /news/svo/svo-2026-10-21/ --source telegram --content repeat
```

Допустимые площадки: `telegram`, `max`; форматы `post`, `repeat`, `pinned`, `comment`, `profile`, `digest`. После `build` готовые ссылки всех материалов находятся в `ops/publish-links.tsv` и `ops/publish-links.json`, заготовки текстов — `ops/posts/telegram/` и `ops/posts/max/`. Эти файлы локальные, **не должны попадать в Git и `dist/`**. При добавлении публикации `articles:prepare` регистрирует отсутствующую кампанию автоматически. Уже существующие UTM-значения не переименовываются, иначе сломалась бы сопоставимость аналитики.

В редакторе Telegram/MAX можно сделать кликабельной строку текста, вставив туда полученную UTM-ссылку. Генератор не публикует сообщение. Подробнее: [ANALYTICS_UTM.md](ANALYTICS_UTM.md), [METRIKA_SETUP.md](METRIKA_SETUP.md).

## 6. Карта: обновить геометрию и получить статистику

1. Сохраните исправленный российский контур в `data/zones.geojson` с **новым реальным временем** `updated` (МСК).
2. Согласуйте `data/map-changes.json`: время первого актуального изменения `zonesUpdated` должно совпадать с `zones.updated`; укажите `title`, `summary`, `details` и, если известен смысл обновления, `kind` (`control`, `cartographic`, `mixed`, `review`). Само изменение геометрии не доказывает военную причину.
3. Выполните `npm run build`. Скрипты добавят срез в `data/map-archive/`, пересчитают статистику и сформируют сводку. **Не редактируйте километры вручную**.
4. Выполните `npm run qa:visible`, затем `PORT=8080 npm run serve:dist` и проверьте карту на компьютере и телефоне: стартовую область, поиск, разные срезы, сравнение, fullscreen, permalink с `lat/lng/z`, сохранение посторонних UTM в URL.
5. В commit сохраните исходную карту, `map-changes.json`, **все новые файлы `data/map-archive/`**, статистику и ожидаемые результаты сборки. `data/map-history/` и `dist/` не коммитить.

**Текст изменения территории для канала:**

```bash
npm run map:post -- --period=latest --source=telegram
npm run map:post -- --month=2026-10 --source=max
```

Возможны `--period=7d`, `30d`, `all`, `month`; доступность периода проверяет команда. На странице `/map/#mapStatistics` под картой также есть выбор дня/месяца и кнопка «Скопировать для канала». Дата расчёта — дата редакционного среза, не гарантированная дата событий на местности; отображаемая площадь — не независимое подтверждение контроля.

При неполной истории Git система использует постоянный архив, но предупреждает о потенциальных пробелах. Сообщения об **исключённых старых несовместимых срезах** не равны сбою текущей карты. Никогда не удаляйте спорные старые данные ради чистого лога. Методология: [MAP_STATISTICS.md](MAP_STATISTICS.md).

## 7. Актуальность справочных памяток

После **реальной проверки** конкретной памятки:

```bash
npm run guides:review -- --id=chto-delat-pri-atake-bpla-lnr --date=YYYY-MM-DD
npm run build
npm run test:freshness
```

Без `--id` команда затронет **все** действующие памятки, поэтому обычному редактору этот режим не нужен. `reviewedAt`/`reviewAfter` отличаются от `dateModified`: последнее повышается только при фактической правке статьи. Ежедневный GitHub Actions предупреждает за семь дней до срока проверки; просрочка блокирует QA. Подробнее: [PUBLICATION_LAYOUT.md](PUBLICATION_LAYOUT.md) и [QUALITY.md](QUALITY.md).

## 8. Сохраняем и публикуем без лишних файлов

Перед commit:

```bash
git status --short
git diff --check
git diff
```

Добавляйте **только осмысленные файлы**: изменённые HTML, JSON-реестры, картинки и производные файлы, которые требует сборка. `editorial/`, временные установщики и чужие ZIP не включайте автоматически. После `git add` обязательно выполните `git diff --cached --check` и `git diff --cached --stat`.

```bash
git commit -m "Publish new material"
git push origin noviy-sait
```

Дождитесь зелёного **Quality** в GitHub Actions. После просмотра страницы и итогового diff можно перенести ветку через pull request либо fast-forward, только если история позволяет. При fast-forward:

```bash
git switch main
git pull --ff-only origin main
git merge --ff-only origin/noviy-sait
git push origin main
```

Workflow **Deploy GitHub Pages** из `main` ещё раз запускает QA, создаёт `dist/` и публикует сайт. **Успешный push не доказывает успешный deploy.** Проверьте GitHub Actions и затем публичную страницу. Откат: исправляющий/revert-коммит и новый deploy, не force-push по умолчанию. См. [PUBLISHING.md](PUBLISHING.md) и [RECOVERY.md](RECOVERY.md).

## 9. Если возникла ошибка

| Сообщение / ситуация | Что делать |
|---|---|
| `QA` будто зависла | Использовать `qa:visible`; полный журнал в `.cache/qa-last.log`; не запускать параллельный QA |
| Нет UTM у новой статьи | `npm run articles:prepare`; существующие кампании останутся неизменными |
| `неизвестная территория` | Выбрать существующую метку в `data/taxonomy.json` или сознательно расширить словарь; **не добавлять произвольный тег** |
| `table without caption`, `inline-style` | Добавить `<caption>`, вынести стили в разрешённый CSS |
| `BODY.html` попадает в публичные страницы | Переименовать редакционный фрагмент в `.fragment` и проверить ссылки скриптов |
| `.gitkeep` в папке изображений | После загрузки настоящих картинок убрать пустую заглушку |
| Повторное подключение иллюстраций сообщает об отсутствии маркера | Проверить HTML: возможно, изображения уже установлены; **не запускать установщик второй раз вслепую** |
| Исторические предупреждения карты | Посмотреть итог команды: WARNING старых срезов ≠ FAIL; геометрию архива не переписывать |
| `npm run qa` не работает на ZIP без `.git` | Восстановить Git для полного исторического QA; `articles:check` работает и без Git |
| `content:check` не пройден | Сравнить изменённый видимый текст и `diff`, только после этого сознательно делать `content:lock` |
| CI зелёный, сайта ещё нет | Проверить отдельно **Deploy GitHub Pages**, а не только **Quality** |
