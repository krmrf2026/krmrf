# Проверка актуальности публикаций KRM РФ

Политика действует с 25 октября 2026 года. Она поддерживает техническую заморозку: исправляется существующая система, новый движок или отдельный каталог публикаций не создаются.

## Что означают даты

- `datePublished` — первоначальная публикация.
- `dateModified` — реальное изменение содержания; не обновляется из-за прохождения сборки.
- `reviewedAt` — дата завершённой редакционной проверки.
- `reviewAfter` — крайний срок следующей проверки, равен reviewedAt плюс reviewCadenceDays.
- `reviewStatus: review-due` — проверка не завершена или срок истёк; это не доказательство ошибки текста.
- `reviewBlocker` — конкретная подтверждённая критическая проблема. Её нельзя снять командой продления дат.

Календарная дата редакции определяется в часовом поясе Europe/Moscow. Расчёт интервалов ведётся по целым календарным датам без летнего времени.

## Сроки

Новый стабильный материал получает исходный интервал 90 дней. Это значение для инструмента, а не разрешение выдавать непроверенный текст за действующий. Существующий срок сохраняется при `guides:review`, если редактор явно не передал другой.

| Содержание | Рекомендуемый интервал | Что проверять раньше срока |
|---|---:|---|
| Номера, адреса, эвакуация, поиск близких | 7–30 дней | Новое объявление ведомства, прекращение работы номера, изменение приёма |
| Выплаты, переходные сроки, бесхозяйное имущество, регистрационные процедуры | 30–60 дней | Поправки, новый перечень территорий, новая форма заявления |
| Общая безопасность без оперативных указаний | 30–60 дней | Новые официальные рекомендации и местные ограничения |
| Стабильная навигация, общие объяснения | 90 дней | Изменение связанной процедуры или структуры сайта |
| Редкое стабильное определение или методология | До 180 дней | Изменение самой методологии; требуется обоснование редактора |
| Историческая сводка или архивный отменённый порядок | Не продлевать как текущую инструкцию | Обнаруженная ошибка исправляется отдельным датированным уточнением |

180 дней — предел валидатора, а не массовый новый срок. В аудите продлён только навигационный хаб недвижимости после проверки его маршрутов. Остальные юридические и контактные страницы не получили фиктивного продления.

## Что блокирует публикацию

Невозможные/будущие даты, неполные поля, неизвестный статус, несогласованный интервал, `current` для непроверенной новой редакции или истёкшего срока, конкретный критический `reviewBlocker` — ошибки QA. Массовая фиксация проверок без ID запрещена.

Обычный корректно обозначенный `review-due` даёт предупреждение и видимое уведомление читателю. Он не блокирует независимый релиз. `npm run build` может только понизить истёкший `current` до `review-due`; даты и интервал остаются прежними. Новую непроверенную редакцию или критическую проблему сборка не маскирует.

Ежедневный `Guide freshness` проверяет очередь со строгим семидневным предупреждением, публикует Summary и отчёт-артефакт на 14 дней. Он намеренно может быть красным при зелёном релизе. Владелец включает уведомления о неуспешных Actions; наличие workflow не доказывает, что уведомления прочитаны.

## Как работать

```bash
npm run guides:report
# Изучить источники одной выбранной публикации, записать основания проверки.
npm run guides:review -- --id=ID --date=YYYY-MM-DD --cadence-days=90
npm run build
# Если содержание действительно менялось, проверить diff и только затем:
npm run content:lock -- --id=ID
npm run content:check
npm run qa:visible
```

Замените ID и дату реальными значениями. Несколько `--id` разрешены только для фактически проверенных публикаций. `reviewedAt` не должен предшествовать последнему содержательному изменению при статусе current.

Проверяются все памятки и другие публикации с явными полями редакционной проверки. Это позволяет контролировать практическую статью с телефонами, сохранив её URL, категорию и тип. Обычные датированные новости не превращаются в вечнозелёные инструкции.

При существенной правке ещё не проверенной памятки редактор сохраняет старую дату проверки, ставит `review-due`, меняет `dateModified` и пишет понятную запись в revisionHistory. Для конкретной опасной ошибки до исправления используется reviewBlocker. После исправления препятствие снимается только осознанным редакционным изменением.

`content:lock -- --id=A` записывает только A. Случайное изменение B остаётся обнаружимым полной `content:check`. Техническая проверка хеша или ссылки не является проверкой закона, контакта либо обстоятельств события.
