# KRM РФ: технический аудит исходного ZIP от 21 октября 2026 года

**Исходник:** `krmrf-main(6).zip`, представлен пользователем 21.10.2026 после синхронизации `main` и `noviy-sait` на коммите `d880c5a`. ZIP сам по себе **не содержит `.git`**. Исследование выполнялось на его извлечённой копии; публичный репозиторий и сайт этим исследованием не изменялись.

## 1. Охват и границы подтверждения

- Просмотрена структура **1 294 файлов**. Архив ~92 МБ, извлечённые файлы ~116 МБ, из них изображения ~85 МБ, данные карты и реестры ~25 МБ.
- Проанализированы **117 HTML-файлов**: 98 зарегистрированных публикаций и 19 других HTML (главная, карты, архив, поиск, категории, служебные и подтверждающие страницы). По каждой HTML-странице собрана отдельная строка в `FULL_SITE_INVENTORY.csv` (название, canonical, H1/H2, метаданные, длина основного текста, картинки и ссылки).
- Типы зарегистрированных публикаций: **47 статей, 28 оценок фронта, 19 памяток, 4 досье**. Разделы: оценки 28, справочник 19, СВО 16, Кременная 16, гражданские последствия 9, досье 4, политика 4, ЛНР 2.
- В 98 основных блоках публикаций: ~1,19 млн символов извлечённого текста, **337 `<img>`**, **45 таблиц**, около **2 609 ссылок** и **989 H2**. Это объём для автоматизированной проверки; ручное фактическое подтверждение каждой войны/юридической суммы/телефона в задачи технического аудита не входит.
- `npm run validate` завершился успешно: **98 публикаций, 117 HTML-страниц, 0 ошибок**. У всех 98 зарегистрированных публикаций присутствуют canonical и описания длиной 50–160 символов, `<title>` в пределах действующего лимита; проверкой относительных путей не выявлены отсутствующие локальные ассеты в HTML публикаций.
- Ограничение: в среде аудита Node **22**, тогда как проект требует **Node 24**, браузерные зависимости Playwright не установлены, исходный ZIP не содержит `.git`. Поэтому полный `npm run qa` с браузером и полная независимая Git-история **не подтверждались здесь**. Предыдущий журнал пользователя показывал успешный QA перед выпуском статьи, но не заменяет повторный QA новой версии после изменений.
- Полевые Core Web Vitals, реальные поисковые позиции, Яндекс.Метрика и работа внешних ссылок в интернете не выводятся из ZIP. Ранжировать публикации по посещаемости без отдельной выгрузки аналитики нельзя.

## 2. Что уже хорошо работает

1. **Статическая архитектура:** контент как HTML, редакционный реестр, отдельная публичная папка `dist`. Нет зависимости сайта от серверной CMS или пользовательской БД.
2. **SEO-контроль:** `data/pages.json`, проверка title, description, H1, canonical, Open Graph/Twitter/JSON-LD, sitemap, внутренних URL, `lastmod` по содержательным датам. Для проверенного архива `validate` чист.
3. **Иллюстрации:** оригиналы и WebP 480/960 с SHA-256, проверка ширин/высот и `srcset`. Все четыре оригинальных изображения статьи 21 октября и восемь производных присутствуют; HTML материала содержит четыре изображения.
4. **Защита текста:** `data/content-integrity.json`, команды `content:lock` и `content:check`; техническая сборка не должна незаметно переписывать содержимое.
5. **Поиск и навигация:** производные поисковый индекс, архив, главная, разделы и соседние переходы. Есть unit/browser тесты и производительные пределы индекса.
6. **Система карты:** 103 пригодных исторических среза, 102 последовательных сравнения, три диагностических окна плюс прочие участки. Постоянный `data/map-archive/` с контрольными суммами; невалидные старые Git-снимки отделены от числового ряда, а не превращены в фальшивый ноль. Непроверенные старые варианты не должны удаляться.
7. **Деплой:** Quality на push рабочей ветки, Pages на `main` после собственного полного QA; публикация только `dist/`. На проверенном архиве `package.json` задаёт Node 24, `fetch-depth: 0` стоит у основных workflows, что важно для истории карты.
8. **Правила безопасности и приватности:** CSP через meta (при ограничениях GitHub Pages), защита от включения исходных реестров/секретов в публичный экспорт, аналитика без передачи текста поискового запроса.

## 3. Выявленные системные дефекты процесса

### P1. Preflight не работал без `.git`

**Воспроизведено:** в исходном ZIP `node tools/preflight-new-articles.mjs` завершался `exit 2` с сообщением «Нет доступной базовой версии HEAD:data/pages.json». Проверка зависела от `git show HEAD:data/pages.json`. В архиве сайта нет `.git`; при уже закоммиченных статьях «новых ID» не было и в обычной Git-копии. Следовательно, сегодняшние ошибки в будущих обновлениях могли вновь проскочить.

**Минимальное исправление:** проверять все 98+ статей без Git, читать точные ключи таксономии, проверять UTM, запрещённые inline-стили, подписи таблиц, canonical, файлы картинок, `.gitkeep` и случайные редакционные `*_BODY.html`. Проверка остаётся читающей по умолчанию.

### P1. Регистрация UTM у новой статьи была ручной

**Воспроизведено в истории пользователя:** после добавления страницы 21 октября `test:utm` падал до ручного добавления `campaigns['svo-2026-10-21']`. В текущем ZIP расхождения уже нет: 98 публикаций и 100 кампаний с двумя системными (`_home`, `_map`). В реестре сохраняются исторические алиасы (например, у недельных оценок); заменять их на новые ID нельзя.

**Исправление:** `npm run articles:prepare` добавляет **только недостающие** ID→ID, если остальные метаданные страницы проходят предварительную проверку; старые имена остаются неизменными. При неверной таксономии или HTML **не записывать UTM** и сначала показать ошибку.

### P1. Предварительная проверка не входила в основной QA

**Воспроизведено:** `package.json` вызывал `images`, `build`, `test:utm`, `validate`, но не `preflight-new-articles.mjs`. Поэтому полный и дорогостоящий импорт истории карты мог отработать раньше очевидной ошибки публикации.

**Исправление:** поместить `articles:check` первой командой `qa`; добавить unit-тесты preflight в `test:ops`. Проверка **не** меняет каталог при QA.

### P2. Проверка QA выглядела зависшей

Причина в практике `npm run qa > /tmp/krm-qa.log 2>&1`: до завершения терминал не показывает прогресс. При этом обработка карты генерирует десятки предупреждений об архивных форматах.

**Исправление:** `npm run qa:visible` запускает тот же неукороченный `qa`, выводит текущий этап и сообщение примерно каждые 20 секунд, сохраняет полный лог в `.cache/qa-last.log` (директория уже исключена из Git), возвращает настоящий exit code. Исторические предупреждения не скрываются из файла и не считаются успехом при красном QA.

### P2. Установочные пакеты не соответствовали ограничениям HTML/CSP

Сегодня на странице выявлялись неизвестная таксономическая метка, таблица без `<caption>`, `style=`, `*_BODY.html`, пустой `.gitkeep`. Исправления уже внесены в коммит `d880c5a` или локальный пакет пользователя; исходный ZIP после публикации проходит `validate`.

**Защита от повторения:** новые ошибки теперь отсекаются ещё на `articles:check`, не переименовывая данные и не удаляя файлы автоматически. Для повторного запуска установщика картинок нужен идемпотентный режим или предварительная проверка маркеров; одноразовые установщики не стоит хранить как постоянную архитектуру.

### P2. Инструкция владельца слишком раздроблена

Прежний README занимал **395 строк**, содержал много повторов и подробностей, уже имеющихся в `PUBLISHING.md`, `MAP_STATISTICS.md`, `ANALYTICS_UTM.md` и `TECHNICAL_FREEZE.md`. Обновлённый README содержит **200 строк**, схему проекта, реальные команды и короткие сценарии, а сложные алгоритмы оставляет профильным документам. Это не замена специализированной документации.

## 4. Предлагаемые автоматизированные операции

| Сценарий | Было | После патча | Сохраняемая защита |
|---|---|---|---|
| Новая статья | Ручные UTM, images, build, проверка | `npm run articles:prepare` | Не переписывает саму статью и старые UTM |
| Проблемная метка/таблица | Ошибка позднего validate | `articles:check` до build | Не подменяет спорную географию |
| ZIP без Git | Предварительная проверка не работает | `articles:check` без `.git` | Полная QA карты всё ещё требует надлежащего репозитория |
| Полный QA | Длинные логи или пустой терминал при redirect | `qa:visible` | Тот же список тестов, тот же exit code |
| История карты | Много старых предупреждений | Короткий прогресс + полный лог | Никакая историческая геометрия не удаляется |
| Публикация GitHub | Ручной `git add/commit/push/merge` | Остаётся под контролем человека | Не делать небезопасный автоматический push в `main` |

Минимальный workflow для одной статьи: подготовить HTML и `pages.json`/изображения → `npm run articles:prepare` → посмотреть изменения → `npm run content:lock` (только после редакционной проверки) → `npm run qa:visible` → посмотреть `dist/` → выборочный commit → проверенный merge/deploy. Скрипт не должен автоматически публиковать непроверенную географию или менять смысл материала.

## 6. Что сознательно не тронуто

- HTML и формулировки **всех** 98 публикаций; исходные изображения; `datePublished/dateModified`.
- Текущая геометрия карты, `zones.updated`, архивные срезы, коэффициенты площади и статистика 29 сентября — 19 октября.
- Перечень UTM-кампаний из опубликованного архива; настройки Метрики и внешние каналы.
- Структура URL, разделы, темы, канонические адреса, CSS/JS интерфейса, GitHub workflows и генератор `dist/`.
- Система контроля содержимого: `content:lock` **не** вызывается автоматически внутри скрипта подготовки, чтобы не узаконить незамеченную порчу текста.

## 7. Ограничения и следующие рекомендации

1. **P1:** установить небольшой патч в рабочую ветку и выполнить полный Node 24 QA и визуальный осмотр; только после этого merge. Это не срочное исправление продакшена с риском отката.
2. **P2:** при следующей новой статье проверить реальный полный цикл `articles:prepare` → `content:lock` → `qa:visible` на тестовой публикации, а потом удалить тестовую публикацию или опубликовать проверенный материал.
3. **P2:** поддерживать аналитическое различие между «проверено скриптом/архивом» и «проверено в реальном браузере/онлайн»: статус ответа сторонних сервисов и достоверность военных сообщений автоматически не устанавливаются.
4. **P3:** исторические предупреждения карты позже можно суммировать в пользовательском терминале, оставляя полный неизменённый журнал. Не удалять невалидные прошлые срезы без отдельного протокола атрибуции.
5. **P3:** не менять техническую архитектуру ради косметического уменьшения лога или создания новой CMS. Соблюдать `TECHNICAL_FREEZE.md`.

**Итог аудита:** существующий сайт уже технически целен и имеет сильные проверки. Основной риск не в SEO-полях сегодняшних страниц, а в ручных шагах при добавлении новых материалов и слишком позднем обнаружении простых ошибок. Предложенный патч устраняет именно этот повторяемый процесс, без переноса сайта на другую платформу.
