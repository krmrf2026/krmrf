# Технический стандарт KRM РФ

Обычная публикация считается готовой после успешного `npm run qa` и ручной проверки сайта. `npm run release` теперь необязательная ручная команда для создания единственного текущего резервного снимка, не условие deploy.

## Автоматические барьеры

- схема, обязательные поля и уникальность метаданных всех публикаций;
- один H1 и неизменность видимого заголовка;
- отдельные SEO-title до 65 символов вместе с брендом;
- descriptions 50–160 символов;
- согласованность canonical, Open Graph, Twitter и JSON-LD;
- отсутствие битых локальных ссылок и изображений;
- реальные размеры изображений, корректные `width`, `height` и `srcset` без искусственного увеличения;
- внутренний реестр старых URL без повторов, конфликтов, битых целей и попадания в sitemap;
- генерация статической страницы для каждого старого URL только в `dist`;
- `noindex`, canonical, мгновенный `meta refresh`, обычная ссылка и JavaScript-перенос query/hash на каждой такой странице;
- запрет `_headers`, `_redirects`, исходных данных и инструментов внутри публичного `dist`;
- точные meta CSP и referrer policy, реально поддерживаемые статическим GitHub Pages;
- запрет исполняемых inline-script, inline event-handler и ложного `frame-ancestors` в meta CSP;
- настоящий Pages workflow, который после полной QA передаёт только `dist` в `upload-pages-artifact` и `deploy-pages`;
- динамический `lastmod` хабов и карты;
- согласованность `zones.geojson`, `map-changes.json` и статичного fallback карты;
- защита карты от устаревших async-ответов при быстрой смене исторических срезов и повторном открытии compare;
- полнотекстовый поисковый индекс v3 с prefix-compression терминов и компактными postings; клиент читает также v2 для безопасного обновления;
- браузерный E2E-поиск: форма, прямой URL, история, нечёткий запрос, ошибка индекса и режим без JavaScript;
- браузерная проверка каждого канонического HTML-маршрута на мобильном и десктопе: геометрия, H1, локальные ресурсы, JavaScript и нарушения CSP;
- мобильное меню, фильтры архива, полноэкранная карта и отсутствие повторов карточек главной;
- перенос старого URL с query/hash и fallback без JavaScript;
- budgets gzip/JS/CSS;
- отсутствие `cache: no-store`, загрузки `pages.json` клиентом и динамической перерисовки каталогов;
- неизменность текстов, ссылок и смысловых `alt` всех публикаций;
- идемпотентность повторной сборки;
- полная очистка `dist` от файлов предыдущего выпуска перед каждым экспортом;
- runtime-тесты модели GitHub Pages: каталог без слеша, статические страницы старых адресов, meta-политики, ETag, методы, удалённые пути, изоляция `dist`, поиск и карта;
- негативные тесты, доказывающие, что валидатор останавливает ошибочный выпуск;
- SHA-256 каждого исходного и адаптивного изображения через `data/image-derivatives.json`;
- при ручном `npm run release`: SHA-256 всех файлов и обоих ZIP, проверка ZIP на повреждение и небезопасные пути.

## Чего проверки сознательно не обещают

GitHub Pages не исполняет `_redirects` и `_headers`. Поэтому стандарт не заявляет серверный CSP, X-Frame-Options или серверный `301` сразу на новый материал. Защита, доступная в статическом HTML, реализована через meta CSP/referrer policy; старые URL сохраняются через статические страницы переноса.

## Бюджеты

- поисковый индекс: не более 600 КБ raw и 150 КБ gzip (исключение от 28 августа 2026 года);
- карта зон: не более 750 КБ raw и 100 КБ gzip;
- архив: raw 145000 + max(0, число публикаций − 87) × 1700 байт (при 97 — 162000); gzip до 25000 байт;
- главная: не более 45 КБ raw и 12 КБ gzip;
- основной собственный JS: до 55000 байт; JS статистики карты отдельно — до 20000 raw и 6000 gzip;
- основной собственный CSS: до 35000 байт; CSS статистики отдельно — до 3000 байт.

Бюджеты являются верхней границей, а не целевым размером.

Vendor/CDN, подложки и Метрика в собственные JS/CSS не включены. test:performance печатает полные собственные суммы. Это контроль размеров, не полевые Core Web Vitals. MapLibre и worker CSP проверяются test:map-dependencies; CDN не покрывается npm audit. test:utm проверяет стабильность кампаний, каналы, готовые посты и отсутствие внутренних UTM. test:freshness-policy проверяет границы предупреждения/просрочки.


## Редакционный контроль после аудита 25 октября 2026 года

Действует `GUIDE_REVIEW_POLICY.md`. Обычная честно обозначенная просрочка не блокирует независимый релиз; `test:freshness` возвращён в QA и проверяет корректность метаданных. Будущие/невозможные даты, ложный `current`, неполные поля и конкретный `reviewBlocker` блокируют проверку. Очередь и семидневное окно предупреждения контролируются отдельным ежедневным workflow.

`npm run guides:report` создаёт JSON и Markdown в `ops/`. Обновлять проверку можно только после чтения источников выбранного материала, например `npm run guides:review -- --id=ID --date=YYYY-MM-DD --cadence-days=90`. Срок не заменяет фактчекинг; контакты и чувствительные правовые процедуры проверяются чаще. Для редкого стабильного объяснения допустимы 180 дней с редакционным обоснованием. Даты исторических сводок не продлеваются.

После осознанного изменения текста: сборка → просмотр diff → `npm run content:lock -- --id=ID` (повторяйте --id для каждого проверенного изменения) → `npm run content:check` → полный QA. Фиксация одной статьи не меняет хеши других. Текущий V5 проверяется для выпусков с 25 октября 2026 года; прежние шаблоны не переписываются. Статья с практическими контактами может участвовать в контроле через явные поля проверки, сохраняя свой тип и URL.
