# KRM РФ — руководство владельца сайта

**Сайт:** https://krmrf.ru/ · **Репозиторий:** https://github.com/krmrf2026/krmrf · **Основа:** r28, рабочий снимок 25.11.2026. Это руководство заменяет прежние отдельные инструкции. Оно объясняет именно текущую архитектуру, а не абстрактный веб-сайт.

## 0. Самое важное: четыре действия на каждый день

1. В существующем Codespaces, в ветке `noviy-sait`, добавьте или отредактируйте исходник публикации и её запись в каталоге. При новой статье положите изображения.
2. Для новой или изменённой статьи выполните подготовку и после просмотра текста закрепите только её ID. Затем выполните `npm run check`. Для технического патча без изменений текста достаточно `npm run check`.
3. Откройте проверенную сборку через `PORT=8080 npm run serve:dist`. В Codespaces откройте порт 8080. После просмотра нажмите Ctrl+C.
4. Проверьте список изменений, добавьте нужные файлы в Git, сделайте commit и push в `noviy-sait`; убедитесь в зелёном Quality. Только после этого перенесите коммит в `main` (команды ниже). Проверьте Pages и живой сайт.

**Не надо каждый день:** переустанавливать Node.js, npm-пакеты и браузеры; делать новую ветку; запускать отдельные release-архивы; обновлять все памятки; редактировать `dist`; очищать Git-историю. Сайт не публикуется одной лишь командой `npm run check`.

## 1. Как устроен проект

Это статический сайт: Git хранит исходники; Node.js собирает их; GitHub Pages отдаёт готовый HTML, CSS, JS и картинки. Нет CMS, PHP, серверной базы данных или обязательного VPS для самого сайта. Telegram-бот работает отдельно.

| Где искать | Что это | Редактировать вручную? |
|---|---|---|
| `news/**/index.html`, `assessment/**/index.html`, `war-crimes/**/index.html` | Содержание каждой опубликованной страницы | Да, при редактировании материала |
| `data/pages.json` | Каталог материалов: ID, URL, H1, SEO, даты, раздел, обложка, таксономия | Да, для новой статьи и значимых правок |
| `data/taxonomy.json` | Разрешённые разделы, темы и географические метки | Только при осознанном расширении словаря |
| `assets/img/` | Оригиналы иллюстраций | Да, класть новые изображения |
| `assets/img/derived/`, `data/image-derivatives.json` | Адаптивные версии картинок и их SHA-256 | Нет: `npm run images` |
| `data/utm-campaigns.json` | Стабильные кампании, каналы Telegram/MAX | Обычно нет: `articles:prepare` добавит отсутствующие ID |
| `ops/publish-links.tsv`, `ops/posts/telegram/`, `ops/posts/max/` | Готовые UTM-ссылки и текстовые заготовки | Нет: `npm run build`; не коммитятся |
| `data/content-integrity.json` | Контроль текста и смысловых подписей публикаций | Нет: `content:lock` после редакционного просмотра |
| `data/zones.geojson`, `data/map-changes.json` | Текущая геометрия карты и описание правки | Да, только совместно |
| `data/map-archive/` | Постоянные исторические срезы и контрольные суммы | Нет вручную; **добавлять новые файлы в Git** |
| `data/map-statistics.json/.csv`, `data/map-history/` | Вычисляемая статистика и кэш выбора срезов | Нет: `npm run build` |
| `data/search-index.json`, `data/site.json`, `sitemap.xml`, карточки разделов | Производные материалы | Нет: `npm run build` |
| `tools/`, `tests/`, `.github/workflows/` | Автоматизация, проверки, развёртывание | Только при доказанной технической необходимости |
| `dist/` | Именно то, что будет опубликовано на GitHub Pages | Нет: создаётся автоматически |

Разделы: СВО (`news/svo/`), Кременная (`news/kremennaya/`), ЛНР (`news/lnr/`), гражданские последствия, политика, памятки, оценки фронта и досье. Поиск, главная, архив, sitemap и переходы между статьями строятся из реестра и текущих HTML. **Текст статей сборка не сочиняет и не сокращает**.

## 3. Новая статья: минимальное число действий

1. Создайте каталог, например `news/svo/svo-YYYY-MM-DD/index.html`, на основе **действующего** материала того же типа и его структуры. Не копируйте старые даты, canonical, JSON-LD, OG-теги и чужую обложку без проверки.
2. Добавьте статью в `data/pages.json`: уникальный `id`, путь `url` со слешами, `type`, `section`, `title` (H1), `seoTitle`, `seoDescription`, `excerpt`, `datePublished`, `dateModified`, `image`, `imageAlt`, подходящие `locations`/`topics`. Метки должны уже существовать в `data/taxonomy.json`.
3. Положите готовые изображения в `assets/img/<раздел>/<статья>/`. Не оставляйте `.gitkeep` в папке картинок. В HTML нужны реальные `src`, `alt`, `width` и `height`. В таблицах обязателен `<caption>`; `style="..."` запрещён строгой CSP. Для промежуточного HTML-фрагмента используйте `.fragment`, **не** `.html`.
4. Запустите единую подготовку:

```bash
npm run articles:prepare
```

Команда добавит **только отсутствующие UTM-кампании** с именем ID статьи (не изменяя старые), подготовит размеры изображений, синхронизирует разделы, поиск, sitemap, карту и ссылки, проверит стабильность UTM-тестами, затем каталог и HTML. Если неизвестна территория, нет картинки или обнаружена запрещённая разметка, команда **остановится с понятной ошибкой**, не подменяя ваши редакционные решения.

5. Просмотрите текст, даты, картинки и diff. Только после проверки осознанного изменения контента обновите контрольную сумму:

```bash
npm run content:lock -- --id=ID
npm run check
```

`content:lock` **не** является способом скрыть неожиданное изменение текста. После успешной полной проверки откройте публичную сборку:

```bash
PORT=8080 npm run serve:dist
```

В Codespaces откройте порт `8080` и проверьте статью, главную, соответствующий раздел, поиск, архив и мобильную ширину. Остановить сервер: `Ctrl+C`.

**Обновление старой статьи:** редактируйте существующий HTML, измените `dateModified` только при реальном изменении содержания, повторите подготовку/просмотр/`content:lock`/QA. Для одной только CSS/JS-правки `content:lock` обычно не нужен.

**Досье на главной и в разделе:** карточки автоматически идут по `dateModified` (при равенстве — по первой публикации); старые `home.dossier` больше не используются. В карточке видны дата обновления и первая публикация. Краткое описание берётся из `excerpt` в `data/pages.json`, поэтому обновляйте его вместе с содержанием, если изменился смысл или число жертв. Сборка не переписывает редакционное описание по произвольному абзацу HTML.

**Новые сообщения Кременского досье:** добавляйте запись в `data/dossier-events.json`, сохраняя прямой внешний источник, `reportedAt`, отдельную `occurredOn` (либо `null`, если дата удара неизвестна), `verifiedAt` и атрибуцию. Таблица в HTML собирается из этого файла; вручную её не редактируют. После реальной проверки измените `dateModified`, описание и журнал редакций досье, выполните сборку и зафиксируйте только его ID. Исторические числа 21/85 не являются накопительным счётчиком; новые сводки без персональной сверки к ним не прибавляются.

**Историческая хроника:** поле `chronicleSeries` используется только для регулярных срезов города, гражданских последствий и общих обзоров. Более ранние выпуски автоматически получают верхнюю ссылку на последний выпуск своей серии. Оценки фронта образуют собственную серию. Эта навигация не меняет исходный текст, дату публикации или дату содержательной правки.

**Редакционная сверка:** памятки и досье сохраняют даты проверки и явные уточнения. `reviewedAt` продлевают только после реального просмотра источников. Ежемесячный workflow составляет необязательную очередь редакции; он не ищет и не публикует новые факты. Досье проверяются по событиям, памятки — по необходимости с плановым ориентиром 180 дней. Успешная техническая проверка не подтверждает достоверность каждого события. Исторический аудит от 07.11.2026 хранится в прежнем коммите и исходном архиве; он не нужен для ежедневной сборки.

## 4. Проверки: что запускать и как видеть прогресс

| Команда | Назначение |
|---|---|
| `npm run articles:check` | Быстрая **читающая** проверка всех зарегистрированных статей без зависимости от `.git` |
| `npm run articles:prepare` | Автоматически восполнить недостающие UTM, обработать изображения, собрать и валидировать |
| `npm run images` | Проверить исходные и производные картинки, SHA-256 и responsive-варианты |
| `npm run build` | Собрать статические разделы, sitemap, поиск, историю и статистику карты, ссылки для публикации |
| `npm run validate` | Проверить HTML, SEO, структуру каталога, таксономию, картинки и ссылки |
| `npm run content:check` | **Только проверить** защиту содержимого, без записи |
| `npm run content:lock -- --id=ID` | Зафиксировать сознательно отредактированное содержимое |
| `npm run check` | Полная QA с прогрессом и негативными сценариями текущего набора. |
| `npm run qa:visible` | Полная `qa`, но с этапами и регулярным индикатором работы; полный журнал `.cache/qa-last.log` |
| `npm run qa` | Та же полная проверка с подробным обычным выводом |
| `npm run test:negative` | Отдельные негативные сценарии валидатора; входит в `npm run check`, не в отдельную `qa` |
| `npm run test:search-e2e` | Проверить поиск в Chromium через Playwright |
| `npm run export:public` | Пересобрать `dist/` из проверенных источников |
| `npm run validate:public` | Проверить публичную сборку `dist/` |

В `qa:visible` нельзя «зависнуть молча»: этап и время выводятся примерно раз в 20 секунд, а весь подробный лог остаётся в `.cache/qa-last.log`. Проверка может быть долгой из-за импорта истории карты и браузерных тестов. **Нельзя запускать две QA одновременно**. Код завершения `0` — успех; любое другое значение — разбирать журнал и не публиковать.

## 5. UTM-ссылки для Telegram и MAX

**Получить обе ссылки на конкретную статью:**

```bash
npm run utm -- --url /news/svo/svo-2026-10-21/ --both
```

**Одну ссылку для повторного поста:**

```bash
npm run utm -- --url /news/svo/svo-2026-10-21/ --source telegram --content repeat
```

Допустимые площадки: `telegram`, `max`; форматы `post`, `repeat`, `pinned`, `comment`, `profile`, `digest`. После `build` готовые ссылки всех материалов находятся в `ops/publish-links.tsv` и `ops/publish-links.json`, заготовки текстов — `ops/posts/telegram/` и `ops/posts/max/`. Эти файлы локальные, **не должны попадать в Git и `dist/`**. При добавлении публикации `articles:prepare` регистрирует отсутствующую кампанию автоматически. Уже существующие UTM-значения не переименовываются, иначе сломалась бы сопоставимость аналитики.

В редакторе Telegram/MAX можно сделать кликабельной строку текста, вставив туда полученную UTM-ссылку. Генератор не публикует сообщение. См. раздел «Аналитика и Метрика».

## 6. Карта: обновить геометрию и получить статистику

1. Сохраните исправленный российский контур в `data/zones.geojson` с **новым реальным временем** `updated` (МСК).
2. Согласуйте `data/map-changes.json`: время первого актуального изменения `zonesUpdated` должно совпадать с `zones.updated`; укажите `title`, `summary`, `details` и, если известен смысл обновления, `kind` (`control`, `cartographic`, `mixed`, `review`). Само изменение геометрии не доказывает военную причину.
3. Выполните `npm run build`. Скрипты добавят срез в `data/map-archive/`, пересчитают статистику и сформируют сводку. **Не редактируйте километры вручную**.
4. Выполните `npm run qa:visible`, затем `PORT=8080 npm run serve:dist` и проверьте карту на компьютере и телефоне: стартовую область, поиск, разные срезы, сравнение, fullscreen, permalink с `lat/lng/z`, сохранение посторонних UTM в URL.
5. В commit сохраните исходную карту, `map-changes.json`, **все новые файлы `data/map-archive/`**, статистику и ожидаемые результаты сборки. `data/map-history/` и `dist/` не коммитить.

**Текст изменения территории для канала:**

```bash
npm run map:post -- --period=latest --source=telegram
npm run map:post -- --month=2026-10 --source=max
```

Возможны `--period=7d`, `30d`, `all`, `month`; доступность периода проверяет команда. На странице `/map/#mapStatistics` под картой также есть выбор дня/месяца и кнопка «Скопировать для канала». Дата расчёта — дата редакционного среза, не гарантированная дата событий на местности; отображаемая площадь — не независимое подтверждение контроля.

При неполной истории Git система использует постоянный архив, но предупреждает о потенциальных пробелах. Сообщения об **исключённых старых несовместимых срезах** не равны сбою текущей карты. Никогда не удаляйте спорные старые данные ради чистого лога. См. раздел «Технические особенности карты».

## 7. Актуальность справочных памяток

После **реальной проверки** конкретной памятки:

```bash
npm run guides:review -- --id=chto-delat-pri-atake-bpla-lnr --date=YYYY-MM-DD
npm run build
npm run test:freshness
```

Без явного `--id` запись запрещена; массового продления дат нет. `reviewedAt`/`reviewAfter` отличаются от `dateModified`: последнее повышается только при фактической правке статьи. Ежемесячный GitHub Actions формирует необязательную сводку; календарный срок не блокирует QA и не изменяет публичную отметку. Критические ошибки метаданных по-прежнему блокируют сборку. См. разделы о редакционной политике и технических проверках.

## 8. Git: как сохранить изменения и опубликовать через терминал

### 8.1. Убедиться, что вы в правильном месте

```bash
pwd
git branch --show-current
git status --short
git log -3 --oneline
```

В норме путь `/workspaces/krmrf`, ветка `noviy-sait`. Если `main`, не редактируйте её: сначала убедитесь, что рабочее дерево чистое, и выполните `git switch noviy-sait`. `git status --short` ничего не выводит, когда нет незафиксированных и неигнорируемых новых файлов. В обозначениях статуса `??` — новый файл, ` M` — изменённый, `M ` — уже добавленный в индекс, `D` — удалённый. Два столбца показывают индекс и рабочее дерево.

В начале новой работы, только когда изменений нет:

```bash
git fetch origin
git pull --ff-only origin noviy-sait
```

Это не скачивает `main` в рабочую ветку насильно. Если `main` ушла вперёд, сначала разберите причины расхождения. Не делайте `reset --hard` или `push --force` ради быстрого исправления.

### 8.2. Что добавлять в Git, а что нет

| Добавлять после проверки | Не добавлять |
|---|---|
| Новый/исправленный `index.html` публикации и `data/pages.json` | `dist/`, `node_modules/`, `data/map-history/` |
| Новые оригинальные изображения и их производные в `assets/img/`, реестр `data/image-derivatives.json` | `.cache/`, `test-results/`, `playwright-report/`, логи |
| `data/content-integrity.json` после выбранного ID; `data/utm-campaigns.json`, сгенерированные страницы рубрик, поиск, sitemap | `ops/posts/`, `ops/publish-links.*`, редакционные отчёты `ops/` |
| Новые файлы постоянного архива `data/map-archive/`, журналы и ожидаемые вычисляемые файлы | ZIP патчей, локальные архивы, фрагменты черновиков, `.env`, ключи и токены |
| Осознанные правки технических файлов и редакционных реестров | Случайные скачивания, личные файлы и приватная выгрузка Метрики |

GitHub ZIP скачивается только из коммитов: незакоммиченная новая статья не попадёт туда. Не удаляйте файлы истории и производные изображения только потому, что они сгенерированы. `.gitignore` работает для неотслеживаемых файлов, но не перестаёт отслеживать уже добавленный секрет. Секрет, попавший в Git, нужно отозвать и отдельно устранить из истории; простое удаление файла не делает его безопасным.

### 8.3. `git add`, `git commit`, `git push` по шагам

```bash
git status --short
git diff --check
git diff --stat
git diff
```

`git diff` показывает изменения отслеживаемых файлов, но не содержимое новых `??`. Просмотрите их в редакторе. Если терминал открыл длинный просмотр, нажмите `q` для выхода.

**Для обычной статьи:** замените `ID` и пути фактическими. `git add` не публикует и не создаёт коммит; он выбирает файлы для него.

```bash
# пример: уже существующие файлы и их удаления, но НЕ новые файлы
git add -u
# добавьте конкретные новые файлы и папки (пример, замените путь)
# git add -- news/reference/ID/index.html assets/img/news/reference/ID/ assets/img/derived/news/reference/ID/
```

Если проверили абсолютно весь вывод `git status --short`, включая каждый новый файл, можно вместо отдельных команд выполнить `git add -A -- .` из корня сайта. Эта команда добавляет новые, изменённые и удалённые неигнорируемые файлы. Для нового материала `git add -u` одного недостаточно! При новой карте проверьте новые постоянные файлы архива. Сначала просмотреть, затем добавить; не наоборот.

```bash
git diff --cached --check
git diff --cached --stat
git status --short
git diff --cached
```

Если выбрали лишний файл, снимите его с индекса без удаления работы:

```bash
# замените путь настоящим именем файла
git restore --staged -- путь/к/файлу
```

Когда всё правильно:

```bash
git commit -m "KRM: краткое описание изменения"
git push origin noviy-sait
git status --short
```

Commit сохраняет только staged-изменения, push отправляет их в рабочую ветку. `Everything up-to-date` означает, что новых коммитов для отправки нет; это не доказательство публикации. `git status --short` после коммита должен быть пуст, если всё действительно сохранили.

### 8.4. Проверка Quality и перенос всего в main

```bash
git fetch origin
gh run list --workflow quality.yml --branch noviy-sait --commit "$(git rev-parse origin/noviy-sait)" --limit 5
```

Если запуск пока не появился, повторите команду позднее. Список по короткому SHA иногда пуст; используйте полный SHA. После зелёного Quality и предварительного просмотра выполните **ровно один безопасный fast-forward** (из `noviy-sait`):

```bash
(
set -e
test "$(git branch --show-current)" = noviy-sait
test -z "$(git status --porcelain)"
git fetch origin
test "$(git rev-parse HEAD)" = "$(git rev-parse origin/noviy-sait)"
git merge-base --is-ancestor origin/main origin/noviy-sait
git push origin origin/noviy-sait:main
git fetch origin
test "$(git rev-parse origin/main)" = "$(git rev-parse origin/noviy-sait)"
echo "PASS: обе удалённые ветки совпадают"
)
```

Это не переключает рабочую ветку, не создаёт новую и не перезаписывает историю. Если проверка предка не прошла или GitHub запретил push, остановитесь: не добавляйте `--force`. При защите ветки используйте разрешённый PR/merge и проверьте его содержимое. Локальная ветка `main` может показывать старый коммит — для публикации важна `origin/main`. При чистом дереве и отсутствии собственных локальных коммитов `main` её можно синхронизировать отдельно:

```bash
git merge-base --is-ancestor main origin/main && git branch -f main origin/main
```

### 8.5. Проверка фактической публикации

```bash
gh run list --workflow pages.yml --branch main --commit "$(git rev-parse origin/main)" --limit 5
```

Нужен успешный **Deploy GitHub Pages** именно для текущего полного SHA. Чтобы увидеть журнал или дождаться результата, возьмите ID из списка:

```bash
# подставьте числовой ID запуска
gh run watch RUN_ID --exit-status
gh run view RUN_ID --log-failed
```

В Pages теперь два задания: `build` (полный check, контрольные суммы, загрузка `dist`) и `deploy` (проверка ID/имени артефакта и официальное размещение). Разные попытки используют разные имена; deploy не подхватывает чужой старый артефакт. При временном сбое deploy можно повторить только неудачное задание, если артефакт ещё доступен. При истечении срока артефакта — повторить весь запуск. Не создавайте пустые коммиты ради перезапуска.

`gh workflow run pages.yml --ref main` требует права Actions: write. Встроенный Codespaces-токен может вернуть HTTP 403; это ограничение прав, а не поломка сайта. В таком случае повторите workflow в GitHub Actions с правами владельца либо используйте отдельную авторизацию CLI, не выдавая токены в чат и не меняя исходники. Официальная документация: https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages . Сбой самого GitHub не гарантируется исправить локальным кодом.

После зелёного deploy откройте `https://krmrf.ru/`, архив, справочник, поиск, новую статью и карту; убедитесь, что версия/новое содержимое совпадает. При необходимости проверка HTTP из терминала:

```bash
for path in / /archive/ /reference/ /search/ /map/ /sitemap.xml /robots.txt; do
  curl -sS -L -o /dev/null -w "%{http_code} %{url_effective}\n" "https://krmrf.ru$path"
done
```

Код 200 показывает ответ HTTP, но не гарантирует правильное отображение или новую редакцию. Старый URL проверяют отдельно: сайт использует статический meta refresh + canonical, а не настоящий HTTP 301. GitHub Pages Settings: Source = GitHub Actions, custom domain `krmrf.ru`, HTTPS включён. Это однократные внешние настройки.

## 9. Как отменить ошибку безопасно

- До `git add`: сначала `git diff -- путь`; если точно хотите отказаться от собственных правок этого файла, `git restore -- путь` (удалит незакоммиченные изменения именно этого файла). Новый файл удаляйте вручную только после проверки.
- После `git add`: `git restore --staged -- путь` убирает файл из будущего коммита, рабочий текст сохраняется.
- После commit/push: обычно создайте исправляющий коммит или `git revert SHA` для конкретного ошибочного коммита. Убедитесь, что не отменяете более поздние полезные правки. Затем check и обычная публикация. При конфликтах остановитесь.
- Если неудачен только deploy, откат кода не нужен: разберите build/deploy и повторите запуск с разрешёнными правами.

**Не использовать автоматически:** `git reset --hard`, `git clean -fdx`, `git push --force`, `rm -rf` по всему репозиторию. Они могут уничтожить незаписанные файлы, зависимости или историю.

## 10. Резервная копия и восстановление

Обычный вариант — ваш существующий ZIP исходников с GitHub или Codespaces. Перед скачиванием убедитесь, что нужные изменения сохранены в нужной ветке. В GitHub ZIP по коммиту нет `.git`, зависимостей, GitHub Secrets и настроек домена. Лучше всего сохранить точный SHA рядом с копией и дату. Если нужен ZIP исключительно отслеживаемых файлов из терминала (не обязательный дополнительный релиз):

```bash
# только если действительно требуется локальная копия; архив вне репозитория
# git archive --format=zip --prefix=krmrf-main/ -o ../krmrf-backup.zip HEAD
```

Скачать сохранённый ZIP на собственный компьютер; облачная копия в том же Codespaces не является независимой. В Windows можно проверить скачанный файл через `Get-FileHash -Algorithm SHA256 путь_к_zip`. Для Git-истории предпочтительна отдельная копия `git clone` на компьютере. Не копируйте токены или личные ключи в открытый ZIP. ZIP исходников сохраняет постоянный архив, но не историю `.git`.

При потере Codespaces создайте рабочую среду из существующего репозитория, а не пустой новый сайт. `git clone` сохраняет историю, `git switch noviy-sait` выбирает рабочую ветку; затем однократная настройка из раздела 2 и `npm run check`. Если GitHub недоступен, распакуйте исходный ZIP отдельно, настройте среду и проверьте сборку; полный исторический аудит без Git имеет ограничения. Никогда не распаковывайте резерв поверх живого рабочего дерева без сравнения. Настройки Pages/DNS/доступы Метрики нужно восстановить отдельно. Техническая проверка и резервное копирование не подтверждают реальную репетицию восстановления.

Система создания `krmrf-source.zip`/`krmrf-public.zip`, `npm run release`, `fixity`, `verify:release`, ручной workflow Release archives и автоматическая очистка старых комплектов удалены. Раньше созданные копии читаются обычными ZIP-инструментами; контрольный файл `SHA256SUMS`, если был в таком архиве, проверяется `sha256sum -c SHA256SUMS` из распакованной папки. `dist/` создаётся при QA, GitHub Pages сам получает его артефакт на один день. Это не дополнительная локальная копия. QA-артефакт с журналом и отпечатками публичных файлов сохраняется в GitHub на 30 дней для диагностики.

### Очистка локального места без риска

```bash
du -sh .cache dist node_modules test-results playwright-report 2>/dev/null || true
git status --short
df -h /workspaces
```

`dist/` нужен для preview; `.cache/` содержит QA-журнал; `node_modules/` нужен для запуска тестов. Не удаляйте их постоянно. Удалять можно только конкретный уже использованный ZIP патча и его временную папку. Весь исходный каталог, изображения, архивы карты и `.git` не являются мусором. На текущем снимке локального кэша в ZIP нет.

## 11. Ошибки и диагностика

| Сообщение / ситуация | Что делать |
|---|---|
| `QA` будто зависла | Использовать `qa:visible`; полный журнал в `.cache/qa-last.log`; не запускать параллельный QA |
| Нет UTM у новой статьи | `npm run articles:prepare`; существующие кампании останутся неизменными |
| `неизвестная территория` | Выбрать существующую метку в `data/taxonomy.json` или сознательно расширить словарь; **не добавлять произвольный тег** |
| `table without caption`, `inline-style` | Добавить `<caption>`, вынести стили в разрешённый CSS |
| `BODY.html` попадает в публичные страницы | Переименовать редакционный фрагмент в `.fragment` и проверить ссылки скриптов |
| `.gitkeep` в папке изображений | После загрузки настоящих картинок убрать пустую заглушку |
| Повторное подключение иллюстраций сообщает об отсутствии маркера | Проверить HTML: возможно, изображения уже установлены; **не запускать установщик второй раз вслепую** |
| Исторические предупреждения карты | Посмотреть итог команды: WARNING старых срезов ≠ FAIL; геометрию архива не переписывать |

| CI зелёный, сайта ещё нет | Проверить отдельно **Deploy GitHub Pages**, а не только **Quality** |

| `No artifacts named github-pages` | Проблема между загрузкой и deploy. Смотрите ID запуска, build и deploy; при доступном артефакте повторите failed jobs. |
| `Resource not accessible by integration` | Недостаточно прав API; не чинится npm или повторным git push. |
| `Permission denied` при push | Проверьте авторизацию и права репозитория; не отключайте защиту ветки ради удобства. |
| `git status` показывает новые файлы после QA | Проверьте, ожидаемые ли это результаты сборки; при неизвестном изменении не коммитьте. |

Полный лог: `tail -n 80 .cache/qa-last.log`. Читающая проверка целостности: `npm run content:check`. При красной QA не публикуйте. Положительный результат на тестах не подтверждает достоверность законодательства, работу внешнего сервиса, полевые Core Web Vitals или фактическую индексацию.

## 12. Редакционная политика — памятки без постоянного переписывания

Политика с 25 ноября 2026 года. KRM РФ публикует датированные материалы и не гарантирует постоянную актуальность всех инструкций. Новые статьи и короткие дополнения предпочтительнее полного переписывания архива.

### Что означают даты

- `datePublished` — первоначальная публикация; URL и дата сохраняются.
- `dateModified` — содержательное изменение или датированное дополнение, а не техническая сборка.
- `reviewedAt` — последняя фактически завершённая сверка источников. Смена политики её не меняет.
- `reviewAfter` — внутренний ориентир: `reviewedAt` плюс `reviewCadenceDays`, а не публичная гарантия. По умолчанию 180 дней, допустимы 1–180 дней. Старые действующие записи переведены на 180 дней без изменения `reviewedAt`.
- `reviewStatus: current` — последняя редакция была сверена, а не подтверждение действующих на сегодня правил. `review-due` — известна необходимость уточнения; архивный и заменённый статусы сохраняются.
- `reviewBlocker` — конкретная критическая проблема. QA по-прежнему блокирует её и недостоверные/несогласованные метаданные.
- `reviewNote` — необязательное датированное дополнение (`date`, `text`, `url`, `label`). Ссылка HTTPS, дата не позже `dateModified`. Блок выводится над исходным текстом и не переписывает его.

Даты рассчитываются по Europe/Moscow. Публичные карточки, поиск и шапки показывают историческую дату сверки, явные предупреждения или архивный статус; отсчёта и обещания «актуально» нет. Внутренний срок не изменяет публичный статус автоматически. Досье проверяются при поступлении новых сведений, без календарного напоминания; совместимые поля сохраняются. Обычные датированные новости не требуют плановой сверки.

### Как работать

Ежемесячный workflow публикует необязательную сводку; корректный календарный срок не блокирует QA. Существенные изменения закона, критические ошибки и недостоверные контакты требуют уточнения по событию, даже до окончания 180 дней. Приоритетные основания указаны в `editorial/review-priorities.json`. По недвижимости отдельно следить за сроком 1 января 2027 года. Просрочка не повод переписывать текст или фиктивно датировать проверку.

Можно выпустить самостоятельную новую статью и добавить ссылку/пояснение к старой. Для `reviewNote` записать дату, короткий текст и источник в реестре, `dateModified`, `revisionHistory` и `review-due`, если полного фактчекинга ещё не было. Известную опасную ошибку нельзя оставить без явного исправления или ограничения применения. В случае замены отметить старую запись `superseded` и `supersededBy`. Для новых дополнений не использовать массовое `content:lock`: исходный текст защищён прежним манифестом.

```bash
# Необязательная сводка
npm run guides:report
# Только после фактической сверки выбранного материала
npm run guides:review -- --id=ID --date=YYYY-MM-DD
npm run build
npm run content:check
npm run check
```

Массовая фиксация дат без ID запрещена. Ручной `--strict-warning` сохранён для диагностики, но не используется в плановом workflow. `--sync-status` сохранён для совместимости команд сборки; он проверяет метаданные, но не меняет статус по календарю. Технические проверки не заменяют проверку закона, контакта или обстоятельств события. Контракт поиска `review: {status, checked, due}` сохранён для Булочкина; старые версии бота могут продолжать показывать свой срок и требуют отдельной корректировки интерфейса.

## 13. Шаблон статьи и технические правила

### Общий каркас

Каждая публикация получает одну внешнюю цепочку хлебных крошек перед `main`,
`container container--content` и один `article.content-card.article`.
Короткое название текущей страницы в крошках сохраняется. Родительские ссылки
соответствуют рубрике; JSON-LD BreadcrumbList согласован с видимой цепочкой.

Первый дочерний блок статьи — `header.article-header`. В нём последовательно
расположены подпись типа, исходный H1, исходные метаданные, редакционная дата
обновления при её наличии и статус актуальности памятки. Существующие `p` и `dl`
внутри компонента метаданных допустимы: их содержание и семантика сохранены,
а положение и отступы согласованы. Редакционные предупреждения, вводные абзацы,
изображения и тематические секции не переписываются.

Последний дочерний блок — один `nav.series-nav`. Он никогда не вложен в последний
тематический раздел статьи и не заменяется неоформленным `article-nav`.

| Тип | Оглавление | Нижние переходы | Особенность |
| --- | --- | --- | --- |
| Оценка | В конце текста, перед series-nav | Соседние оценки по дате публикации | Существующее зелёное оформление, период и статус сохранены |
| Материал о Кременной | Перед первым основным разделом | Соседние материалы Кременной по дате публикации | Исторические статьи сохраняют свою структуру и содержание |
| Другие статьи | Перед первым основным разделом | Соседние статьи той же рубрики | Гражданские последствия, СВО, ЛНР и политика не смешиваются |
| Памятка | Перед первым основным разделом | Существующий тематический подбор | Статус актуальности после метаданных; нет ложной хронологии |
| Досье | Перед первым основным разделом | По дате публикации, а не дате события | Существующее красное оформление сохранено |

### Оглавление

Оглавление строится из H2 в порядке чтения. Ссылки используют существующие ID;
у заголовка без ID добавляется свободный `content-section-N`. Имеющиеся ID
не переименовываются и не удаляются. Названия пунктов совпадают с текущими H2.
Заключение, связанные материалы и источники не теряются из навигации.

Отдельный датированный блок редакционного обновления не считается основным
разделом оглавления. При менее чем трёх остальных H2 оглавление не добавляется.
Так сохраняется отсутствие лишнего оглавления у трёх ранних коротких материалов.
Вводные блоки вне основного раздела остаются перед оглавлением. Если весь основной
текст заключён в одну секцию, оглавление стоит перед этой секцией; саму секцию
сборка не разрезает и не переписывает.

### Соседние и связанные публикации

Существующий компонент series-nav получает полные текущие названия из каталога.
Добавление очередной оценки или статьи автоматически обновляет переход предыдущей.
Пропущенные календарные недели не превращаются в несуществующие ссылки.
У первого/последнего материала свободную позицию занимает ссылка на раздел
с подписью «Раздел», без притворного «следующего» или «предыдущего» материала.

У памяток сохраняются существующие тематические цели и осмысленные подписи
«Базовая памятка», «По сроку», «Контакты города» и т. п. Общие подписи
«Предыдущий/Следующий материал» заменяются на «Связанная памятка», поскольку
эта рубрика смешивала тематический подбор и хронологию. Если нижнего блока ещё
нет, используются до двух ссылок из авторского раздела связанных памяток;
при отсутствии такой подборки остаётся ссылка на справочник. Новые рекомендации
из содержания автоматически не изобретаются.

### Что проверяется

`npm run validate` теперь проверяет каркас всех публикаций, полноту и положение
оглавлений, соседние переходы, совпадение подписей с каталогом, метаданные,
крошки, responsive sizes, а также одинаковые шапки и футеры всех страниц.
Это проверка, а не автоматическое исправление не прошедшего валидацию HTML.

`npm run test:uniformity` проверяет поисковое состояние, задержанную загрузку
индекса, сброс, историю, сохранение сторонних URL-параметров, полную выдачу,
даты в результатах и повторяемость нормализации всего каталога.
Команда включена в `npm run qa`. Браузерные сценарии находятся в
`tests/e2e/uniformity.spec.mjs` и выполняются штатным Playwright вместе с остальными.
Негативные тесты намеренно восстанавливают выявленные поломки и требуют отказа валидатора.

### Сохранность содержания и новый выпуск

Алгоритм и формат `content-integrity-v2` не ослаблены и не заменены. Старый контроль
учитывает также текст оглавлений и ссылки навигации. Поэтому после осознанного
добавления/редактуры публикации сначала нужно собрать служебные блоки, затем
зафиксировать проверенный результат:

```bash
npm run images
npm run build
npm run content:lock -- --id=ID
npm run qa
```

Не запускайте `content:lock` просто для подавления неожиданного изменения текста.
Сначала просмотрите diff.

При добавлении статьи продолжают использоваться HTML и `data/pages.json`.
Новая структура данных, CMS, маршруты, источники контента и сервисы не вводятся.
Даты публикаций и `lastmod` от технической унификации не повышаются.


## 14. Аналитика и Метрика

### Аналитика и UTM KRM РФ

#### Задача

Схема нужна для двух вопросов:

1. откуда человек пришёл на сайт — Telegram, MAX, поиск или другой источник;
2. что он сделал после входа — достиг глубины страницы, нажал ссылку следующего материала, воспользовался картой или поиском.

Счётчик Яндекс.Метрики: `110383043`.

#### Почему без дополнительного хранения UTM

Яндекс.Метрика определяет источник визита по меткам на **первом просмотре страницы в визите**. Поэтому KRM РФ не копирует UTM во внутренние ссылки и не сохраняет их отдельно в `localStorage`/`sessionStorage`: стандартной атрибуции Метрики достаточно, а адреса сайта остаются чистыми.

Это также означает: если человек сначала открыл сайт напрямую, а затем в том же визите перешёл по размеченной ссылке, источник уже может остаться первоначальным. Это нормальная логика визита Метрики, а не ошибка сайта.

#### Единый UTM-протокол

##### Telegram

- `utm_source=telegram`
- `utm_medium=messenger`

##### MAX

- `utm_source=max`
- `utm_medium=messenger`

`telegram` входит в список распознаваемых Метрикой мессенджеров. `max` нужен как стабильное собственное значение источника: даже если Метрика относит его к «другому мессенджеру по меткам», в отчёте UTM источник остаётся различимым как `max`.

`utm_campaign` — постоянное имя материала или кампании. Реестр data/utm-campaigns.json сохраняет старые кампании по прежнему slug; новые получают неизменяемый id публикации. Смена URL не требует переименования кампании.

`utm_content` используется только для типа размещения:

- `post` — основной пост;
- `repeat` — повторная публикация;
- `pinned` — закреп;
- `comment` — ссылка в комментарии;
- `profile` — ссылка в профиле/описании;
- `digest` — подборка.

`utm_term` сейчас не используется: у проекта нет задачи размечать платные ключевые слова, а лишнее поле только дробит отчёты.

#### Генератор ссылок

Telegram:

```bash
npm run utm -- --url /news/civilian-impact/bpla-lnr-2026-10-02/ --source telegram --content post
```

MAX:

```bash
npm run utm -- --url /news/civilian-impact/bpla-lnr-2026-10-02/ --source max --content post
```

Сразу обе ссылки:

```bash
npm run utm -- --url /news/civilian-impact/bpla-lnr-2026-10-02/ --both --content post
```

Повтор той же статьи не получает новую кампанию:

```bash
npm run utm -- --url /news/civilian-impact/bpla-lnr-2026-10-02/ --both --content repeat
```

Генератор сохраняет обычные query-параметры и `#fragment`, удаляет старые `utm_*` и создаёт одну согласованную разметку.

#### События сайта

| Идентификатор | Что измеряет |
| --- | --- |
| `read_50` | просмотрено не менее 50% публикации |
| `read_90` | просмотрено не менее 90% публикации |
| `read_depth` | совместимое техническое событие с параметром `percent=50/90` |
| `content_continue` | клик по другому внутреннему URL из публикации; якоря той же страницы не считаются |
| `home_route` | переход с главной на другой внутренний URL |
| `search_submit` | выполнен поиск; передаются только длина и число слов, не текст запроса |
| `search_result_click` | открыт результат поиска |
| `map_action` | действие на карте |
| `channel_click` | переход с сайта в Telegram или MAX |
| `source_click` | переход по внешнему источнику; передаётся только hostname, не полный URL |

Код не создаёт новый счётчик, не включает Вебвизор/карту кликов и не добавляет отдельные идентификаторы пользователя.

#### Что один раз сделать в Метрике

Создать цели типа «Целевое событие» с точными идентификаторами:

```text
read_50
read_90
content_continue
home_route
search_submit
search_result_click
map_action
channel_click
source_click
```

`read_depth` отдельной целью не нужен: он оставлен для совместимости и анализа параметра процента.

Также в настройках счётчика полезно включить фильтр **«Не учитывать мои визиты»** для рабочего браузера владельца. При проверке целей тогда использовать инкогнито.

#### Основной отчёт

`Отчёты → Источники → Метки UTM`.

Иерархия:

```text
utm_source → utm_medium → utm_campaign → utm_content
```

К этому отчёту добавляются метрики нужных целей: `read_50`, `read_90`, `content_continue`, `map_action` и т. д. Так сравниваются не сырые клики, а качество визитов по Telegram/MAX и по конкретным постам.

#### Страницы входа

Для проверки landing pages выгружать **таблицу страниц входа**, а не временной график одной выбранной серии. Нужны как минимум:

```text
Страница входа · Визиты · Посетители · Источник · Отказы · Глубина · Время
```

Если выгрузка снова показывает только `https://krmrf.ru/`, сначала проверять настройки отчёта/группировки. Код сайта уже подключает один и тот же `metrika.js` ко всем обычным HTML-страницам, а валидатор после этого патча запрещает выпуск страницы без счётчика и noscript-пикселя.

#### Правила

1. Для ссылок на сайт из Telegram/MAX использовать генератор, а не собирать UTM руками.
2. Одно и то же содержательное размещение всегда писать одинаково: `telegram`, `max`, `messenger`, `post`, `repeat` и т. д.
3. Не создавать новую `utm_campaign` для каждого повтора одной статьи.
4. Не размечать внутренние ссылки сайта UTM-метками.
5. Не передавать через цели имена, телефоны, сообщения пользователей, поисковые фразы и полные внешние URL.
6. После релиза проверять цели через отладчик Метрики (`?_ym_debug=2`) и затем в отчётах.

#### Автоматическая сборка

Build создаёт все ссылки и тексты в ops/publish-links.json, ops/publish-links.tsv, ops/posts/telegram/<id>.md и ops/posts/max/<id>.md. Для новой статьи ручные метки не нужны. Канал добавляется одной записью channels реестра. Результаты не входят в dist и не коммитятся. Редактор публикует подготовленный текст; Quality/Pages показывают ссылки последних десяти материалов. В сводке карты выберите канал перед копированием. CLI: `npm run map:post -- --source=max --content=post`. Обычные UTM остаются видны в URL. Файл не доказывает отправку поста или визит.

read_50/read_90 — достигнутая высота страницы без учёта времени чтения. content_continue — клик, а не подтверждённая загрузка. Однократная настройка: раздел «Метрика» ниже. Приватный сбор: [automation/private-analytics/README.md](automation/private-analytics/README.md).

#### Разметка источников и смысл channel_click в r26

`channel_click` фиксирует только `https://t.me/xykrm` и `https://max.ru/xykrm` с допустимым завершающим слешем. Посты проекта и каналы ведомств не считаются переходом в собственный канал. Источники и официальные сервисы в тексте или таблице отмечаются атрибутом `data-source` на ссылке либо на смысловом блоке; прежние `.source-list` и `li[id^="src-"]` продолжают работать. Атрибут не меняет URL и не добавляет UTM.

Пример для нового материала: `<a href="https://example.org/document" data-source>Документ источника</a>`. Отмечайте только ссылку на источник или официальный сервис. Фотокредиты, лицензии, внутренние переходы и собственные каналы не размечаются как источники. Телефоны и email не вызывают `source_click`. Событие передаёт только host и размещение, без полного URL.

Начиная с фактического deploy r26 охват source_click расширяется, а channel_click сужается до собственных каналов. Изменение числа целей через эту границу нельзя автоматически трактовать как изменение интереса читателей.

#### Контроль одного гражданского дайджеста

Для одного выпуска с одинаковой посадочной страницей зафиксируйте дату, время, площадку и место ссылки. Пример двух ссылок для памятки о регистрации (Telegram и MAX).

```bash
npm run utm -- --url /news/reference/egrn-2026-05-15/ --both --campaign digest_egrn_r28 --content post
```

| Что записать | Единица и источник |
|---|---|
| Вход из размещения | Визиты из Метрики по utm_source, utm_medium, utm_campaign, utm_content |
| Полезный визит | Визиты на выбранную памятку с guide_action, с той же входной меткой |
| Выход с сайта в канал | Визиты с channel_click по Telegram и MAX отдельно |
| Подписка по приглашению | Число из статистики конкретной пригласительной ссылки в кабинете канала, когда оно доступно |

Снимайте данные размещения через 24 и 72 часа, затем за 28 закрытых дней. Введите фактический часовой пояс и одинаковые границы окон. Сохраняйте исходные числители, число входов, даты и пропуски. Если статистика приглашений отсутствует, оставьте ячейку пустой. При нескольких размещениях используйте разное разрешённое значение utm_content или отдельные кампании.

### Однократная настройка Метрики и автоматического хранения

Существующий счётчик: **110383043**, сайт `https://krmrf.ru/`. Изменения исходников не создают цели в аккаунте и не восстанавливают прошлые визиты. Для следующих действий нужны права владельца/представителя.

#### 1. Счётчик и цели

В настройках проверьте адрес сайта, дополнительные адреса и часовой пояс МСК. Новый счётчик не создавайте. Запишите текущие фильтры своих визитов/роботов и даты их изменения, чтобы сравнения оставались воспроизводимыми.

Создайте только недостающие цели типа **JavaScript-событие / Целевое событие**, условие **«совпадает»**, с точными идентификаторами:

| Идентификатор | Значение |
|---|---|
| `read_50` | Нижняя граница экрана достигла 50% высоты публикации |
| `read_90` | Нижняя граница экрана достигла 90% высоты публикации |
| `content_continue` | Клик на другой внутренний URL из публикации |
| `home_route` | Клик с главной на внутреннюю страницу |
| `search_submit` | Отправлен локальный поисковый запрос |
| `search_result_click` | Нажат результат поиска |
| `map_action` | Действие с инструментом карты |
| `channel_click` | Переход в собственный канал KRM РФ: t.me/xykrm или max.ru/xykrm |
| `source_click` | Клик на размеченный внешний источник или официальный сервис из материала |
| `guide_action` | Клик на явно размеченное действие пилотной памятки |
| `guide_feedback` | Добровольный ответ Да/Нет в пилотной памятке |

Правильно настроенные существующие цели используйте повторно. Названия могут быть понятными русскими; идентификаторы должны совпадать посимвольно. `read_depth` отдельной целью не нужен. Скролл не доказывает внимательное чтение; клик не подтверждает успешную загрузку следующей страницы. `channel_click` измеряет выход с сайта, а вход из мессенджера определяется UTM. Цели начинают собираться после настройки, задним числом не восстанавливаются.

#### 2. Сохранённые отчёты

Откройте **Отчёты → Источники → Метки UTM**. Выберите период фактических постов/переходов, снимите старые сегменты и ограничения выбранными страницами. Группировки: UTM Source → UTM Medium → UTM Campaign → UTM Content, при необходимости страница входа.

Метрики: визиты, посетители, просмотры, отказы, глубина, время, целевые визиты read_50/read_90/content_continue/map_action. Зафиксируйте МСК, модель последнего перехода и одинаковые фильтры; приватный API-комплект использует `last*`-измерения. Ожидаются `telegram`/`max`, `messenger`, постоянная кампания и тип размещения `post`/`repeat` и др. MAX может попасть в категорию другого мессенджера, но UTM Source остаётся различимым.

Сохраните также «Источники, сводка», «Страницы входа», «Страницы выхода», «Новые/вернувшиеся» с одинаковыми параметрами. Выгружайте всю таблицу, а не один ряд графика. Историческое расхождение посещаемости и источников на 24 визита нельзя объяснить исходниками: повторно сравните одни целые сутки без сегментов, затем подключайте фильтры по одному. Не складывайте дневных уникальных пользователей для получения недельных; группы пользователей также пересекаются.

#### 3. Контрольный переход

После Pages deploy получите тестовую ссылку:

```bash
npm run utm -- --url /news/reference/egrn-2026-05-15/ --source telegram --campaign qa_20261018_telegram_01 --content post
```

Для более позднего теста поменяйте дату/номер. Разместите ссылку в тестовом сообщении Telegram и сделайте **один** переход в чистом сеансе браузера. Для MAX используйте новый отдельный сеанс и кампанию `qa_YYYYMMDD_max_01`. Перед этим не открывайте сайт в данном сеансе: метки определяются по первому просмотру визита. Предпросмотр ботом не равен визиту человека. Массовые тестовые переходы не нужны.

Проверьте наличие четырёх UTM-параметров на посадочной странице. В DevTools → Network должна загрузиться `mc.yandex.ru/metrika/tag.js?id=110383043` и уйти первый просмотр `/watch/110383043` с адресом размеченной страницы. Не должно быть блокировки CSP/расширением. Для событий используйте официальный отладчик `?_ym_debug=2`, при уже существующем query — `&_ym_debug=2`.

После обработки данных найдите тестовую campaign в UTM-отчёте. Если Network успешен, а строки нет, проверьте период, МСК, сегменты, фильтры своих визитов/роботов и модель. Запишите время МСК и итоговый URL; cookies/токены из HAR не публикуйте. Мгновенное появление строки не гарантируется. На основном рабочем браузере можно включить «Не учитывать мои визиты»; тест тогда выполняйте в другом чистом сеансе. `qa_*` исключайте из рабочих сравнений одинаковым сохранённым сегментом; при добавлении API-фильтра сверяйте итог с интерфейсом.

## 15. Технические особенности карты

Описание ниже сохраняет методологию существующего проекта и ограничения интерпретации сохранённых данных. Не меняйте исторические срезы или правила подсчёта в рамках обычной технической уборки.

### Статистика карты KRM РФ

#### Проверка полного ряда и районы карты — r24

При загрузке проверяются все соседние срезы, их порядок, IDs, даты, баланс добавлений/исключений и совпадение дневных и месячных сводок с полным рядом. Повреждённый или обрезанный JSON не заменяет проверенную статичную сводку; копирование остаётся доступным. Выбор дня охватывает весь архив, при этом таблица последних дней остаётся компактной.

Календарный день формируется из частей даты в МСК с григорианским календарём и латинскими цифрами. Строковое представление даты в мобильном браузере не меняет порядок срезов и принадлежность обновления к месяцу.

В `data/map-statistics-config.json` заданы три непересекающихся диагностических окна: Красный Лиман и окрестности, Волчанск и восточные окрестности, Орехов и восточные окрестности. Это условные географические границы, а не официальные границы военных направлений. Изменения вне окон относятся к «Остальным участкам», поэтому суммарные добавления и снятия согласованы с полной картой. Пересекающиеся окна, повторные ID и некорректные координаты блокируют сборку.

Для каждого последовательного обновления вычисляется точное пересечение добавленной и снятой российской геометрии с окнами тем же сферическим методом. Учтены все российские features, MultiPolygon, отверстия, перекрытия и повторные перекрасы. Дневная и месячная разбивка суммирует все обновления периода, а не только последнее снятие или изменение одного большого фрагмента. В архиве и исходных координатах правок нет; число +467,3 км² не заменяется ожидаемым знаком.

Публичный блок «По районам» закрыт по умолчанию и появляется только при изменениях в именованных районах. Текст для канала содержит их баланс. Общий итог относится ко всей карте. На доступных срезах 31 августа — 29 сентября 2026 года в выбранном лиманском окне снято 297,8 км² и добавлено 67,7 км², баланс −230,1 км². В волчанском окне баланс +157,9 км², в ореховском +100,6 км². Числа описывают опубликованную окраску; фактическую дату изменения контроля они не устанавливают.

Исходники клиентского JavaScript занимают менее 20 КБ; отдельный бюджет передаваемого gzip — 6 КБ. Дополнительная проверка ряда использует один форматтер дат и индекс обновлений по дням, чтобы не перебирать всю историю для каждого календарного дня. Новых зависимостей нет. Версия ассетов r24 предотвращает использование закэшированного старого клиента с новым блоком.

На `/map/#mapStatistics` под картой добавлен блок изменений площади. Он показывает добавления, исключения и чистое изменение российского контура по сохранённым срезам. В публичном блоке остаются последнее обновление, выбор дня и месяца, три показателя, кнопка «Скопировать для канала» и закрытые по умолчанию текст поста и таблицы. CSV, журнал импорта, предупреждения Git и технические пояснения из интерфейса убраны. Архив, JSON/CSV и проверки сохранены для расчётов и воспроизводимости результатов.

#### Как обновлять и получать пост

1. Измените `data/zones.geojson`; задайте новое, более позднее `updated`.
2. Добавьте согласованную запись в `data/map-changes.json`: `zonesUpdated`, `title`, `summary`, `details`. Укажите `kind`, если природа правки известна: `control`, `cartographic`, `mixed`, `review`. Без него сохраняется `unknown`; геометрия сама не устанавливает причину изменения.
3. Выполните `npm run build`. Сохранятся новый срез и рассчитанная сводка; вручную площади не вводятся.
4. Проверьте `npm run qa` в штатной среде проекта и страницу из `dist/`.
5. В статистике выберите период и нажмите «Скопировать для канала». Предварительно открывать текст не требуется. Полученный текст — редакционный черновик; публикация выполняется человеком.
6. Сохраните в commit изменения карты, новый журнал/файлы `data/map-archive/` и ожидаемые результаты сборки. `data/map-history/` и `dist/` в Git не сохраняются.

Локальный черновик последнего обновления:

```bash
npm run build
node tools/map-post.mjs --period=latest > map-post.txt
```

Другие варианты:

```bash
node tools/map-post.mjs --month=2026-10
node tools/map-post.mjs --period=7d
node tools/map-post.mjs --period=30d
node tools/map-post.mjs --period=all
npm run map:statistics
npm run test:map-statistics
npm run map:verify
```

`map:post` воспроизводимо проверяет исходные срезы, текущую геометрию, JSON/CSV и статичную сводку перед получением текста. Изменение контура без нового времени или устаревшая статистика блокируют генерацию. Для проверки всей геометрии/сводки используйте `map:verify`; перед публикацией новых данных выполняйте `build` и полный `qa`. Чтобы забрать только текст без заголовков npm, используйте показанный вызов `node`.

#### Постоянная история

`data/map-archive/journal.json` содержит записи пригодных состояний (`versions`), сохранённых противоречивых вариантов (`ambiguousVersions`) и ссылки на неизменные GeoJSON с SHA-256. При сборке объединяются постоянный журнал, имеющийся кэш селектора, все доступные версии `data/zones.geojson` в истории текущего Git checkout и текущая карта. Старые Git-версии с одинаковым временем и разными геометриями/охватами группируются до расчёта: без независимо сохранённой публикации дата не входит в числовой ряд, все варианты остаются в архиве. Изменение уже сохранённой текущей карты без новой даты по-прежнему блокирует запись. Возврат A → B → A сохраняется как три состояния. Проверка без изменения геометрии с новым временем тоже сохраняется и может давать настоящий ноль.

В селекторе карты остаются последние 24 состояния (настройка `KRM_MAP_HISTORY_LIMIT`, 2–48). Этот лимит не обрезает постоянный журнал и статистику. Последовательные одинаковые геометрии могут не дублироваться в селекторе; в постоянном журнале они остаются. После изменения охвата для нового среза используйте новое значение `statistics.scopeVersion` и согласованное описание конфигурации; сравнение разных версий охвата даёт пропуск, а не ложный прирост.

Сборка без `.git` воспроизводится из постоянного архива. Workflow используют `fetch-depth: 0`; при shallow-копии сохраняется предупреждение о неполной Git-истории. Недатированные/неразбираемые старые версии Git перечисляются как неимпортированные, без выдуманных дат. Непригодная старая геометрия не считается нулевым состоянием и описывается в журнале исключений; повреждение текущей карты или сохранённых архивных файлов останавливает сборку. Новые записи из локальной сборки следует сохранять вместе с картой: пересоздание истории только в CI не гарантирует сохранение промежуточных состояний после squash/rebase.

Импорт дополнительного исходного среза:

```bash
node tools/map-history.mjs --import=/absolute/path/old-zones.geojson
npm run build
```

У GeoJSON должно быть корректное `updated`, которое не позднее текущей опубликованной карты. Прошлое не надо заменять сегодняшним временем: это изменило бы хронологию. Более старый текущий файл поверх нового архива блокируется; редакционный возврат геометрии оформляется новым временем.

#### Что измеряется

Метод `krmrf-spherical-sweep-v1` фиксирован. Измеряется объединение Polygon/MultiPolygon с именами слоя `russian`, `rf`, `россия`, `рф`; отверстия вычитаются, перекрытия считаются один раз.

Для соседних состояний A и B отдельно измеряются B\A (добавлено) и A\B (исключено). Итог = площадь B − площадь A; он проверяется против добавлено − исключено. Для нескольких обновлений добавления/исключения суммируются по соседним сравнениям: участок, меняющийся повторно, может попасть в сумму несколько раз. Итог за период остаётся разностью конечной и начальной площади. Поэтому нулевой итог не доказывает отсутствия изменений.

Расчёт использует вертикальное разбиение границ, сферу радиуса 6 371 008,8 м и аналитический интеграл `R² · ∫(sin φверх − sin φниз) dλ`. Рёбра в этой модели линейны в координатах долготы/широты. Ориентации проверяются целочисленными предикатами; внутри вычисления координаты округляются до 10⁻¹⁰ градуса. Исходные файлы и визуальный контур не упрощаются. Значение модельное: другой радиус/эллипсоид/интерполяция могут дать другие числа; пересчитывать часть ряда другим методом нельзя.

Самопересечения, незамкнутые/пустые кольца, некорректные отверстия, неподходящие координаты, антимеридиан и широты вне ±85° не исправляются молча. Ошибка вычисления останавливает сборку. Отсутствие российского слоя не трактуется как нулевая площадь контроля. Контрольные суммы и геометрия каждого среза проверяются; `map:verify` заново воспроизводит JSON, CSV и статичную сводку.

На экране числа округляются до 0,1 км²; малые значимые ненулевые значения обозначаются `<0,1`. Показатели округляются независимо, итог вычисляется до округления: видимое «добавлено − исключено» может отличаться от показанного итога на 0,1 км². В JSON/CSV остаются неокруглённые модельные результаты. Округление не означает точность оценки реального контроля до 0,1 км².

#### Дни, месяцы и пределы выводов

- Дата числа — дата публикации конечного среза, не дата боевого события. Все времена отображаются как МСК; старые отметки без часового пояса приняты за UTC+03:00. Если это предположение неверно, требуется отдельная миграция дат всей истории.
- Старые отметки вида `2026-05-18 8:08` разбираются как `2026-05-18 08:08` МСК. Исходное `updated` и геометрия сохраняются без изменения. Минуты, календарная дата и диапазон часов проверяются строго; отсутствующая дата не восстанавливается из времени commit. Ранее пропущенная пригодная Git-ревизия импортируется при сборке и удаляется из текущего списка исключений.
- День без среза = `no_snapshot` и пустые числовые поля, а не 0 км² и не «фронт не менялся». Публичная дневная таблица показывает только дни публикаций и известных непригодных состояний за последние 30 календарных дней до последнего среза; пустые и будущие дни не достраиваются. В данных пропуски остаются пропусками. Исходная запись без предыдущего среза — `baseline`.
- Изменение между 3 и 8 октября не распределяется искусственно по пяти дням. В таблице 8 октября указан весь интервал 3 → 8 октября.
- Месячная сводка группирует обновления по дате конечного среза. Интервал 26 сентября → 3 октября входит в опубликованные октябрьские обновления и явно помечен пересечением границы месяца. Это не установленная площадь перехода за календарный октябрь. Для отделения событий по месяцам нужен промежуточный срез.
- Если начало периода не покрыто, показывается доступная часть. Для 7/30 дней до последнего среза может понадобиться исходное опубликованное состояние раньше начала окна; обе фактические даты и предупреждение выводятся в посте CLI. Эти режимы убраны из публичного интерфейса.
- Текущий слой измеряется целиком, без маски Украины и без отдельного слоя ВСУ. Его общая площадь не является показателем «площадь Украины под контролем РФ». Уменьшение зоны РФ не доказывает прирост контроля ВСУ: возможны неопределённая зона, исправление контура или другие причины.
- `kind=cartographic` учитывается в числах и обозначается в тексте. При `unknown` причину изменения не устанавливаем. Наличие новых цифр не заменяет независимой проверки редакционного описания.

#### Доставка данных и проверки

Расчёт выполняется при сборке; клиент получает компактные готовые данные. Сборка создаёт статичную сводку, которая читается без JavaScript. JSON/CSV и HTML получают согласованный ключ версии; данные другой версии не подменяют текущую сводку. При ошибке/тайм-ауте загрузки выбор периода отключается, сохранённая сводка остаётся доступной. При отказе Clipboard API блок текста автоматически открывается, текст выделяется для ручного копирования. Кнопка доступна и при ошибке загрузки JSON: копируется сохранённый текст именно этой версии страницы.

Экспорт публикует статистику, постоянный журнал и геометрии; служебные настройки и инструменты в публичную сборку не включаются. Клиентская статистика имеет отдельные бюджеты JS 20 КБ raw / 6 КБ gzip, CSS 3 КБ; исходные бюджеты остальных файлов сохранены, JSON ограничен 5 МБ.

Тесты покрывают аналитические площади, пересечения, отверстия, острова, дубликаты, порядок колец, повреждения, баланс, A → B → A, пропуски, полночь/месяц/часовой пояс, полный Git сверх лимита селектора, миграцию кэша, повторяемость, клиентский выбор, сбой сети, смешение версий и копирование. Двенадцать Playwright-сценариев проверяют компактный интерфейс, выбор дня/месяца, копирование и его резервный вариант, сбой загрузки, ширины 320/360/390/430 пикселей и статичную сводку без JavaScript. Общий браузерный контракт проекта также проверяет всю страницу карты.

#### Исправление импорта истории от 11 октября 2026 года

Сборка различает три ситуации: коммит без файла карты, непригодный старый срез и ошибка чтения Git. Коммит без файла не является нулевой картой. Старый GeoJSON без даты, распознанного слоя РФ или корректной геометрии не включается в расчёт; его полный commit, дата (когда установлена), SHA-256 прочитанного содержимого, названия слоёв и причина сохраняются в `skippedRevisions` постоянного журнала. Неизвестные имена слоёв не переименовываются автоматически. Поле `kind=absent` означает отсутствие файла в коммите, `kind=unusable` — прочитанный, но непригодный для расчёта GeoJSON.

В дневной таблице известная дата исключённого среза внутри доступного ряда помечается «Нет сопоставимых данных»; числовые поля остаются пустыми. Если исключённое состояние лежит между двумя пригодными срезами, сравнение их контуров остаётся доступным, но интерфейс и черновик поста предупреждают, что промежуточные добавления и исключения полностью не восстановлены. Несколько непригодных ревизий одного времени считаются одной пропущенной датой среза; если для этого времени есть пригодное состояние, пропуска даты нет. Журнал ревизий сохраняет каждое исключение отдельно.

Удалённый или недоступный Git-объект, ошибка чтения дерева/истории, существующий пустой файл карты, изменение уже сохранённой текущей карты без новой даты, повреждённая текущая карта, явный импорт или постоянный архив останавливают сборку. Противоречивые старые Git-версии обрабатываются отдельно, как описано ниже. Данные не подменяются нулями. Перед созданием новых архивных файлов проверяются все неизменные пути. Штатная конфигурация времени — МСК (`Europe/Moscow`, старое время без пояса `+03:00`); изменение этих правил требует явной миграции.

Старое повреждённое описание `map-changes.json` не удаляет пригодную геометрию: неподдерживаемые поля не используются, причина остаётся `unknown` и выводится предупреждение. Текущее редакционное описание и метаданные постоянного архива проверяются строго. Пригодность исторической геометрии проверяется до группировки; конфликт дат сохраняется в отдельном архиве и не выдаётся за неподдерживаемый формат.

Импортируется вся доступная история файла, достижимая из `HEAD` текущей ветки, включая слитые ветки (`git log --full-history`). Экспериментальные несоединённые ветки автоматически не импортируются. `gitMode=shallow` явно показывает неполный clone, `unavailable` — отсутствие Git, `available-head-ancestry` — доступную историю текущей ветки; последнее не доказывает полноту всех когда-либо опубликованных версий сайта. Уже сохранённый архив сохраняется при сокращении истории clone. Отсутствующий Git у ZIP-копии допускается; неисправный имеющийся репозиторий не считается отсутствием Git.

Дополнительные регрессионные проверки запускаются командой `npm run test:map-history` и включены в `npm run qa`. Они создают собственные временные Git-репозитории; объекты и данные основного проекта не изменяют.

#### Противоречивые даты: дополнительное исправление 11 октября 2026 года

В старом Git несколько разных корректных карт могут иметь одно `updated`, например `2026-03-13T05:50:00.000Z`. Это время не устанавливает порядок публикации. Сборка не выбирает первый/последний Git-коммит, не подменяет дату временем commit и не разносит варианты по выдуманным минутам.

- Для каждой даты сравнивается пара «хеш геометрии + версия охвата». Одинаковая пара в нескольких коммитах не является противоречием, даже если форматирование JSON различается.
- Без независимого подтверждения все разные варианты даты сохраняются в `ambiguousVersions` и исключаются из `versions`/сравнений. GeoJSON хранится в обычном постоянном архиве без изменения геометрии и данных; сериализация JSON нормализована. Записи содержат дату, охват, SHA-256, хеш геометрии и происхождение. Для соответствующих Git-коммитов `skippedRevisions.kind=ambiguous` содержит полный commit, SHA-256 исходного содержимого Git, ссылку на сохранённый вариант, число вариантов и `resolution=unresolved`.
- Ранее сохранённая текущая карта (`published-map`), исходное состояние из загруженного архива с SHA-256 в `sourceRefs` (`archive:...@sha256:...`) и явный редакционный импорт (`import:...`) устанавливают конкретный срез. Он остаётся в `versions`, альтернативы сохраняются в `ambiguousVersions`, а исключённые ревизии отмечаются `resolution=anchored`. Это не восстановление остальных промежуточных публикаций и не доказательство боевых событий. Пометки происхождения — часть проверяемого журнала; не присваивайте их предполагаемым данным вручную.
- Сам факт ранее выполненного импорта из Git или наличие среза в кэше селектора не подтверждает, какой вариант публиковался. Если после fetch найден второй контур того же времени, ранее импортированный Git-срез переводится в `ambiguousVersions` вместе с новым вариантом. Его файл и происхождение сохраняются. Неопределённость сохраняется при последующих shallow-сборках и работе без Git.
- Спорная дата считается один раз в `omittedSnapshotCount`, сколько бы ревизий ни было. День с неизвестным состоянием получает `unavailable` и пустые числовые поля. Календарь включает известные непригодные/спорные даты даже раньше первого пригодного среза, вплоть до текущей карты. Месячная таблица показывает дни с неполными данными. Месяц без двух сопоставимых срезов не получает числовую оценку.
- Между двумя пригодными срезами через спорную дату можно сравнить конечные контуры. Дневная сводка относит результат ко всему фактическому интервалу; интерфейс, CSV и пост предупреждают, что промежуточные добавления/исключения восстановлены не полностью. Результат не распределяется по пропущенным дням.

Разрешайте спорную дату только при наличии самостоятельно проверенного исходного опубликованного состояния: используйте явный `--import` этого GeoJSON. Это редакционный выбор, который записывается в происхождение; альтернативный вариант не удаляется. Перед получением поста выполните `npm run build`. Контрольные суммы спорных файлов проверяют как импорт истории, так и генератор статистики/поста.

Нельзя исправлять эту ошибку массовой заменой `updated` старых файлов или удалением постоянного архива. Для установки дополнительного патча поверх предыдущего исправления используется обычный `git apply --check`, затем `git apply` и штатный `npm run qa`.

#### Компактный интерфейс и мобильная версия

Периоды публичного блока: последнее обновление, день публикации карты и месяц публикаций. День объединяет все сопоставимые обновления с конечной датой в выбранном дне по МСК; многодневный интервал не делится на вымышленные суточные изменения. Для дня без сопоставимых состояний показывается «нет данных», а не ноль. Месяцы без опубликованных сопоставимых изменений и без известных проблемных состояний не заполняют список пустыми строками.

Даты, суммы и короткий текст поста формирует общее ядро на сервере сборки и в браузере. В посте остаются период, три числа, ссылка на карту и необходимые условные оговорки о неполном периоде, переходе месяца, пропусках и правках контура. Данные о контроле ВСУ не выводятся как измеренная площадь. Числа и геометрическая методика не меняются.

На экранах до 680 px показатели и строки таблиц перестраиваются в вертикальные записи. Селекторы имеют шрифт 16 px и высоту не менее 46 px, кнопка — 48 px и полную ширину. Текст и таблицы закрыты по умолчанию; копирование находится перед ними. В тестах проверяются ширины 320, 360, 390 и 430 px, выбор дня/месяца, буфер обмена, отказ загрузки, несовпадение версии данных и ручное копирование при отказе Clipboard API.

### Чего проверки сознательно не обещают

GitHub Pages не исполняет `_redirects` и `_headers`. Поэтому стандарт не заявляет серверный CSP, X-Frame-Options или серверный `301` сразу на новый материал. Защита, доступная в статическом HTML, реализована через meta CSP/referrer policy; старые URL сохраняются через статические страницы переноса.

### Бюджеты

- поисковый индекс: не более 600 000 байт raw и 150 000 + max(0, число публикаций − 107) × 2 000 байт gzip;
- карта зон: не более 750 КБ raw и 100 КБ gzip;
- архив: raw 145000 + max(0, число публикаций − 87) × 1700 байт (при 97 — 162000); gzip до 25 000 + max(0, число публикаций − 107) × 200 байт;
- главная: не более 45 КБ raw и 12 КБ gzip;
- основной собственный JS: суммарно до 64 000 байт, на проверяемой странице до 55 000 байт; JS статистики карты отдельно — до 20000 raw и 6000 gzip;
- основной собственный CSS: до 35000 байт; CSS статистики отдельно — до 3000 байт.

Бюджеты являются верхней границей, а не целевым размером.

Vendor/CDN, подложки и Метрика в собственные JS/CSS не включены. test:performance печатает полные собственные суммы. Это контроль размеров, не полевые Core Web Vitals. MapLibre и worker CSP проверяются test:map-dependencies; CDN не покрывается npm audit. test:utm проверяет стабильность кампаний, каналы, готовые посты и отсутствие внутренних UTM. test:freshness-policy проверяет границы предупреждения/просрочки.

### Связь с Булочкиным и поиском

Сайт отдаёт `/data/search-index.json` (существующий формат v3, клиент понимает также v2). В карточках поиска используются канонические URL, `description` и совместимый блок `review` с полями status/checked/due. Не переименовывайте поля ради косметики. Булочкин должен читать description с fallback на excerpt, а `due` воспринимать как внутренний ориентир, не публичную гарантию. Изменение сайта само по себе не обновляет бота на VPS. Если синхронизация недоступна, бот должен использовать последнюю проверенную локальную копию и явно сообщать дату; фактическая реализация проверяется на VPS отдельно.
