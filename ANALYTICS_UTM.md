# Аналитика и UTM KRM РФ

## Задача

Схема нужна для двух вопросов:

1. откуда человек пришёл на сайт — Telegram, MAX, поиск или другой источник;
2. что он сделал после входа — достиг глубины страницы, нажал ссылку следующего материала, воспользовался картой или поиском.

Счётчик Яндекс.Метрики: `110383043`.

## Почему без дополнительного хранения UTM

Яндекс.Метрика определяет источник визита по меткам на **первом просмотре страницы в визите**. Поэтому KRM РФ не копирует UTM во внутренние ссылки и не сохраняет их отдельно в `localStorage`/`sessionStorage`: стандартной атрибуции Метрики достаточно, а адреса сайта остаются чистыми.

Это также означает: если человек сначала открыл сайт напрямую, а затем в том же визите перешёл по размеченной ссылке, источник уже может остаться первоначальным. Это нормальная логика визита Метрики, а не ошибка сайта.

## Единый UTM-протокол

### Telegram

- `utm_source=telegram`
- `utm_medium=messenger`

### MAX

- `utm_source=max`
- `utm_medium=messenger`

`telegram` входит в список распознаваемых Метрикой мессенджеров. `max` нужен как стабильное собственное значение источника: даже если Метрика относит его к «другому мессенджеру по меткам», в отчёте UTM источник остаётся различимым как `max`.

`utm_campaign` — постоянное имя материала или кампании. Реестр data/utm-campaigns.json сохраняет старые кампании по прежнему slug; новые получают неизменяемый id публикации. Смена URL не требует переименования кампании.

`utm_content` используется только для типа размещения:

- `post` — основной пост;
- `repeat` — повторная публикация;
- `pinned` — закреп;
- `comment` — ссылка в комментарии;
- `profile` — ссылка в профиле/описании;
- `digest` — подборка.

`utm_term` сейчас не используется: у проекта нет задачи размечать платные ключевые слова, а лишнее поле только дробит отчёты.

## Генератор ссылок

Telegram:

```bash
npm run utm -- --url /news/civilian-impact/bpla-lnr-2026-10-02/ --source telegram --content post
```

MAX:

```bash
npm run utm -- --url /news/civilian-impact/bpla-lnr-2026-10-02/ --source max --content post
```

Сразу обе ссылки:

```bash
npm run utm -- --url /news/civilian-impact/bpla-lnr-2026-10-02/ --both --content post
```

Повтор той же статьи не получает новую кампанию:

```bash
npm run utm -- --url /news/civilian-impact/bpla-lnr-2026-10-02/ --both --content repeat
```

Генератор сохраняет обычные query-параметры и `#fragment`, удаляет старые `utm_*` и создаёт одну согласованную разметку.

## События сайта

| Идентификатор | Что измеряет |
| --- | --- |
| `read_50` | просмотрено не менее 50% публикации |
| `read_90` | просмотрено не менее 90% публикации |
| `read_depth` | совместимое техническое событие с параметром `percent=50/90` |
| `content_continue` | клик по другому внутреннему URL из публикации; якоря той же страницы не считаются |
| `home_route` | переход с главной на другой внутренний URL |
| `search_submit` | выполнен поиск; передаются только длина и число слов, не текст запроса |
| `search_result_click` | открыт результат поиска |
| `map_action` | действие на карте |
| `channel_click` | переход с сайта в Telegram или MAX |
| `source_click` | переход по внешнему источнику; передаётся только hostname, не полный URL |

Код не создаёт новый счётчик, не включает Вебвизор/карту кликов и не добавляет отдельные идентификаторы пользователя.

## Что один раз сделать в Метрике

Создать цели типа «Целевое событие» с точными идентификаторами:

```text
read_50
read_90
content_continue
home_route
search_submit
search_result_click
map_action
channel_click
source_click
```

`read_depth` отдельной целью не нужен: он оставлен для совместимости и анализа параметра процента.

Также в настройках счётчика полезно включить фильтр **«Не учитывать мои визиты»** для рабочего браузера владельца. При проверке целей тогда использовать инкогнито.

## Основной отчёт

`Отчёты → Источники → Метки UTM`.

Иерархия:

```text
utm_source → utm_medium → utm_campaign → utm_content
```

К этому отчёту добавляются метрики нужных целей: `read_50`, `read_90`, `content_continue`, `map_action` и т. д. Так сравниваются не сырые клики, а качество визитов по Telegram/MAX и по конкретным постам.

## Страницы входа

Для проверки landing pages выгружать **таблицу страниц входа**, а не временной график одной выбранной серии. Нужны как минимум:

```text
Страница входа · Визиты · Посетители · Источник · Отказы · Глубина · Время
```

Если выгрузка снова показывает только `https://krmrf.ru/`, сначала проверять настройки отчёта/группировки. Код сайта уже подключает один и тот же `metrika.js` ко всем обычным HTML-страницам, а валидатор после этого патча запрещает выпуск страницы без счётчика и noscript-пикселя.

## Правила

1. Для ссылок на сайт из Telegram/MAX использовать генератор, а не собирать UTM руками.
2. Одно и то же содержательное размещение всегда писать одинаково: `telegram`, `max`, `messenger`, `post`, `repeat` и т. д.
3. Не создавать новую `utm_campaign` для каждого повтора одной статьи.
4. Не размечать внутренние ссылки сайта UTM-метками.
5. Не передавать через цели имена, телефоны, сообщения пользователей, поисковые фразы и полные внешние URL.
6. После релиза проверять цели через отладчик Метрики (`?_ym_debug=2`) и затем в отчётах.

## Автоматическая сборка

Build создаёт все ссылки и тексты в ops/publish-links.json, ops/publish-links.tsv, ops/posts/telegram/<id>.md и ops/posts/max/<id>.md. Для новой статьи ручные метки не нужны. Канал добавляется одной записью channels реестра. Результаты не входят в dist и не коммитятся. Редактор публикует подготовленный текст; Quality/Pages показывают ссылки последних десяти материалов. В сводке карты выберите канал перед копированием. CLI: `npm run map:post -- --source=max --content=post`. Обычные UTM остаются видны в URL. Файл не доказывает отправку поста или визит.

read_50/read_90 — достигнутая высота страницы без учёта времени чтения. content_continue — клик, а не подтверждённая загрузка. Однократная настройка: [METRIKA_SETUP.md](METRIKA_SETUP.md). Приватный сбор: [automation/private-analytics/README.md](automation/private-analytics/README.md).

## Разметка источников и смысл channel_click в r26

`channel_click` фиксирует только `https://t.me/xykrm` и `https://max.ru/xykrm` с допустимым завершающим слешем. Посты проекта и каналы ведомств не считаются переходом в собственный канал. Источники и официальные сервисы в тексте или таблице отмечаются атрибутом `data-source` на ссылке либо на смысловом блоке; прежние `.source-list` и `li[id^="src-"]` продолжают работать. Атрибут не меняет URL и не добавляет UTM.

Пример для нового материала: `<a href="https://example.org/document" data-source>Документ источника</a>`. Отмечайте только ссылку на источник или официальный сервис. Фотокредиты, лицензии, внутренние переходы и собственные каналы не размечаются как источники. Телефоны и email не вызывают `source_click`. Событие передаёт только host и размещение, без полного URL.

Начиная с фактического deploy r26 охват source_click расширяется, а channel_click сужается до собственных каналов. Изменение числа целей через эту границу нельзя автоматически трактовать как изменение интереса читателей.
