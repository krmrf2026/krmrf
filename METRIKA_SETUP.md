# Однократная настройка Метрики и автоматического хранения

Существующий счётчик: **110383043**, сайт `https://krmrf.ru/`. Изменения исходников не создают цели в аккаунте и не восстанавливают прошлые визиты. Для следующих действий нужны права владельца/представителя.

## 1. Счётчик и цели

В настройках проверьте адрес сайта, дополнительные адреса и часовой пояс МСК. Новый счётчик не создавайте. Запишите текущие фильтры своих визитов/роботов и даты их изменения, чтобы сравнения оставались воспроизводимыми.

Создайте только недостающие цели типа **JavaScript-событие / Целевое событие**, условие **«совпадает»**, с точными идентификаторами:

| Идентификатор | Значение |
|---|---|
| `read_50` | Нижняя граница экрана достигла 50% высоты публикации |
| `read_90` | Нижняя граница экрана достигла 90% высоты публикации |
| `content_continue` | Клик на другой внутренний URL из публикации |
| `home_route` | Клик с главной на внутреннюю страницу |
| `search_submit` | Отправлен локальный поисковый запрос |
| `search_result_click` | Нажат результат поиска |
| `map_action` | Действие с инструментом карты |
| `channel_click` | Переход в собственный канал KRM РФ: t.me/xykrm или max.ru/xykrm |
| `source_click` | Клик на размеченный внешний источник или официальный сервис из материала |

Правильно настроенные существующие цели используйте повторно. Названия могут быть понятными русскими; идентификаторы должны совпадать посимвольно. `read_depth` отдельной целью не нужен. Скролл не доказывает внимательное чтение; клик не подтверждает успешную загрузку следующей страницы. `channel_click` измеряет выход с сайта, а вход из мессенджера определяется UTM. Цели начинают собираться после настройки, задним числом не восстанавливаются.

## 2. Сохранённые отчёты

Откройте **Отчёты → Источники → Метки UTM**. Выберите период фактических постов/переходов, снимите старые сегменты и ограничения выбранными страницами. Группировки: UTM Source → UTM Medium → UTM Campaign → UTM Content, при необходимости страница входа.

Метрики: визиты, посетители, просмотры, отказы, глубина, время, целевые визиты read_50/read_90/content_continue/map_action. Зафиксируйте МСК, модель последнего перехода и одинаковые фильтры; приватный API-комплект использует `last*`-измерения. Ожидаются `telegram`/`max`, `messenger`, постоянная кампания и тип размещения `post`/`repeat` и др. MAX может попасть в категорию другого мессенджера, но UTM Source остаётся различимым.

Сохраните также «Источники, сводка», «Страницы входа», «Страницы выхода», «Новые/вернувшиеся» с одинаковыми параметрами. Выгружайте всю таблицу, а не один ряд графика. Историческое расхождение посещаемости и источников на 24 визита нельзя объяснить исходниками: повторно сравните одни целые сутки без сегментов, затем подключайте фильтры по одному. Не складывайте дневных уникальных пользователей для получения недельных; группы пользователей также пересекаются.

## 3. Контрольный переход

После Pages deploy получите тестовую ссылку:

```bash
npm run utm -- --url /news/reference/egrn-2026-05-15/ --source telegram --campaign qa_20261018_telegram_01 --content post
```

Для более позднего теста поменяйте дату/номер. Разместите ссылку в тестовом сообщении Telegram и сделайте **один** переход в чистом сеансе браузера. Для MAX используйте новый отдельный сеанс и кампанию `qa_YYYYMMDD_max_01`. Перед этим не открывайте сайт в данном сеансе: метки определяются по первому просмотру визита. Предпросмотр ботом не равен визиту человека. Массовые тестовые переходы не нужны.

Проверьте наличие четырёх UTM-параметров на посадочной странице. В DevTools → Network должна загрузиться `mc.yandex.ru/metrika/tag.js?id=110383043` и уйти первый просмотр `/watch/110383043` с адресом размеченной страницы. Не должно быть блокировки CSP/расширением. Для событий используйте официальный отладчик `?_ym_debug=2`, при уже существующем query — `&_ym_debug=2`.

После обработки данных найдите тестовую campaign в UTM-отчёте. Если Network успешен, а строки нет, проверьте период, МСК, сегменты, фильтры своих визитов/роботов и модель. Запишите время МСК и итоговый URL; cookies/токены из HAR не публикуйте. Мгновенное появление строки не гарантируется. На основном рабочем браузере можно включить «Не учитывать мои визиты»; тест тогда выполняйте в другом чистом сеансе. `qa_*` исключайте из рабочих сравнений одинаковым сохранённым сегментом; при добавлении API-фильтра сверяйте итог с интерфейсом.

## 4. История вне браузера

В `automation/private-analytics/` находится готовый Python/Actions-комплект. Создайте отдельный **приватный** репозиторий и скопируйте туда Python-файлы и README в корень, `analytics.yml` — в `.github/workflows/analytics.yml`. Включите Issues и Actions, настройте notifications об ошибках.

Получите OAuth-токен с `metrika:read` по официальной инструкции https://yandex.ru/dev/metrika/ru/intro/authorization . Токен сохраните только в Settings → Secrets and variables → Actions → `METRIKA_OAUTH_TOKEN`. Не вставляйте токен в чат, публичные файлы и аргументы команд. В workflow уже указан счётчик 110383043 и проверка приватности до обращения к API.

Запустите Run workflow вручную. Успех: появились `data/daily`, `data/periods`, `data/health.json`, `reports/latest.md`. Сверьте один полный день и одну неделю с интерфейсом при одинаковых настройках. Затем проверьте первый автоматический запуск.

Расписание: ежедневно 03:17 UTC / 06:17 МСК, возможна задержка GitHub. Обновляются семь закрытых суток, последние три предварительные. Ежедневно сравнение 7/7; по понедельникам также 28/28 и 90/90, недельное Issue в приватном репозитории. Без OAuth и успешной приёмки комплект ещё не является подключённой системой.

## Критерии завершения

Версия r25 опубликована, нужные URL открываются 200, карта показывает настоящую подложку и контуры; девять целей сопоставлены; две одиночные кампании видны после обработки; приватный экспорт прошёл вручную и по расписанию, итог согласуется с интерфейсом; настроено уведомление о потере доступа.

## Изменение событий 19 октября 2026 года

После установки r26 `channel_click` относится только к главной странице собственного канала KRM РФ. Ссылки на ведомства и их посты относятся к источникам, если размечены в материале. Данные до и после фактической публикации r26 сравнивайте с учётом этой границы; дата подготовки патча не является датой его публикации.

Сохраните существующие цели `source_click` и `channel_click`. Изменение исходников не требует их пересоздания. После deploy проверьте в отладчике Метрики один переход к МЧС из таблицы БПЛА, один к Росреестру из текста и один в канал KRM РФ. Первые два должны дать `source_click`, последний — `channel_click`. Локальный E2E проверяет вызов; приём события подтверждается только в вашем счётчике. Исторически неотправленные цели задним числом не появятся.
